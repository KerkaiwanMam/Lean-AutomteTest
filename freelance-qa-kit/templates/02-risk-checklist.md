# 02 · Risk Checklist — เช็กลิสต์ตามความเสี่ยง

> ใช้หลัง intake เพื่อตัดสินว่า **จะใช้เวลาตรงไหน** · คะแนนความเสี่ยง = ผลกระทบ (Impact) × โอกาสเกิด (Likelihood)
> แนวคิด risk-based testing มาจาก ISTQB CTFL v4.0.1 หัวข้อ 5.2 · รายการ "จุดอ่อนของเว็บที่สร้างด้วย AI" ด้านล่างเป็น **ประสบการณ์/ข้อสังเกตทั่วไป ไม่ใช่ผลวิจัย** — ปรับตามเคสจริงที่เจอ

---

## ส่วนที่ 1 · Risk map (ทำ 30 นาที)

ให้คะแนน 1–3: Impact (1 = รำคาญ, 2 = เสียลูกค้าบางส่วน, 3 = เสียเงิน/ข้อมูลรั่ว/ใช้ไม่ได้) · Likelihood (1 = น่าจะไม่เกิด, 2 = อาจเกิด, 3 = น่าจะเกิด)

| Risk ID | พื้นที่ / Flow | สิ่งที่อาจผิด | Impact | Likelihood | คะแนน | ระดับ |
|---|---|---|---|---|---|---|
| R-01 | เช่น การจองคิว | จองซ้ำช่วงเวลาเดียวกันได้ | 3 | 2 | 6 | สูง |
| R-02 | | | | | | |

**ระดับ:** 6–9 = **สูง** (ลงลึก + เขียน test case + automate) · 3–4 = **กลาง** (exploratory + เช็กลิสต์) · 1–2 = **ต่ำ** (ดูผ่านๆ หรือข้าม)

**การแบ่งเวลา:** สูง ≈ 60% · กลาง ≈ 30% · ต่ำ ≈ 10%

## ส่วนที่ 2 · เช็กลิสต์ (ติ๊กตามแพ็กเกจ)

สัญลักษณ์แพ็กเกจ: **S** = Smoke · **L** = Launch · **D** = Deep · ✅ ผ่าน · ❌ ไม่ผ่าน (เปิด finding) · ➖ ไม่เกี่ยว/ไม่ได้ตรวจ

### A. Critical flows (S L D)
- [ ] ทุก flow ใน intake ส่วน B ทำได้ตั้งแต่ต้นจนจบ บน browser หลัก
- [ ] ผลลัพธ์ **ถูกบันทึกจริง** (รีเฟรชแล้วยังอยู่, ล็อกอินอีกเครื่องแล้วเห็น, แอดมินเห็น) — ไม่ใช่แค่ UI แสดงว่าสำเร็จ
- [ ] อีเมล / การแจ้งเตือนที่ flow บอกว่าจะส่ง ส่งจริงและข้อมูลถูกต้อง
- [ ] ชำระเงิน (test mode): สำเร็จ, ถูกปฏิเสธ, ยกเลิกกลางทาง — สถานะคำสั่งซื้อตรงกับผลจริง

### B. Input และ edge case (S L D)
- [ ] ช่องบังคับเว้นว่าง, ค่ายาวมาก, อักขระพิเศษ/ภาษาไทย/emoji, ตัวเลขติดลบ/ศูนย์/ทศนิยม
- [ ] ค่าขอบ (boundary) ของตัวเลข วันที่ จำนวน — เช่น จองวันที่ผ่านมาแล้ว, จำนวน 0, เกินสต็อก
- [ ] กดปุ่มส่งซ้ำเร็วๆ / ดับเบิลคลิก → ไม่สร้างรายการซ้ำ
- [ ] ปุ่ม Back / รีเฟรช ระหว่าง flow
- [ ] Validation ทำที่ **server** ด้วย ไม่ใช่แค่ฟอร์ม (L D: ลองส่งผ่าน DevTools หรือ Postman)

### C. Authentication และสิทธิ์ — จุดที่เว็บ AI มักพลาด (S L D)
- [ ] หน้า/ API ที่ต้องล็อกอิน เข้าไม่ได้เมื่อไม่ได้ล็อกอิน (เปิด URL ตรงใน incognito)
- [ ] **User A เห็น/แก้ข้อมูลของ User B ไม่ได้** — เปลี่ยน ID ใน URL หรือใน API request (IDOR)
- [ ] User ธรรมดาเข้าหน้า/ API ของแอดมินไม่ได้
- [ ] Logout แล้ว session ใช้ต่อไม่ได้, รีเซ็ตรหัสผ่านทำงานและลิงก์ใช้ซ้ำไม่ได้
- [ ] (L D) ถ้าใช้ Supabase/Firebase: ตาราง/collection มีกฎ (RLS / Security Rules) — ลองอ่านตารางด้วย anon key จาก browser

### D. ความปลอดภัยพื้นฐาน (S L D) — passive เท่านั้น และต้องมีการอนุญาตในส่วน D ของ intake
- [ ] ไม่มี secret ใน JavaScript ฝั่ง client (เช่น `sk_live_`, `service_role`, AWS key, private key) — automated: `security-basics.spec.ts`
- [ ] ใช้ HTTPS ทุกหน้า, cookie ของ session มี `Secure` `HttpOnly` `SameSite`
- [ ] Security headers หลัก (CSP, X-Content-Type-Options, frame-ancestors/X-Frame-Options, HSTS) — บันทึกเป็น Medium/Low ตามบริบท
- [ ] หน้า error ไม่แสดง stack trace / ข้อความจากฐานข้อมูล
- [ ] (L D) ZAP baseline scan (passive) — แนบผลสรุป ไม่ต้องรายงานทุก warning

### E. UI, responsive, browser (S L D)
- [ ] มือถือกว้าง 375px: ไม่มี scroll แนวนอน, ปุ่มกดได้, เมนูเปิดได้ — automated: `responsive.spec.ts`
- [ ] Browser ที่ intake ระบุ (อย่างน้อย Chrome + Safari/WebKit)
- [ ] Loading, empty, error state มีและสื่อความหมาย (ปิดเน็ต/ทำให้ API ล้ม แล้วดู)
- [ ] ข้อความ placeholder ของ AI ค้างอยู่ไหม (Lorem ipsum, "Your Company", ลิงก์ `#`, รูปตัวอย่าง)

### F. Accessibility (L D)
- [ ] axe-core WCAG 2.1 A/AA ไม่มี violation ระดับ serious/critical บนหน้าหลัก — automated: `a11y.spec.ts`
- [ ] ใช้งาน flow หลักด้วยคีย์บอร์ดอย่างเดียวได้, เห็น focus
- [ ] รูปสำคัญมี alt, ฟอร์มมี label
- หมายเหตุ: เครื่องมืออัตโนมัติจับปัญหาได้ไม่ครบ (Deque 2021 รายงาน 57% ตามปริมาณ issue; GOV.UK 2017 พบ 29% ของปัญหาที่ตั้งไว้ไม่มีเครื่องมือใดจับได้) จึงต้องมีการตรวจด้วยมือ

### G. Performance เบื้องต้น (L D)
- [ ] Lighthouse (mobile) ของหน้าแรกและหน้า flow หลัก — บันทึก LCP / CLS / ขนาดรูป
- [ ] รูปภาพใหญ่เกินจำเป็น, โหลด script ไม่ใช้, API ช้าเกิน ~2 วินาทีใน flow หลัก

### H. ข้อมูล ความเป็นส่วนตัว เนื้อหา (L D)
- [ ] มีหน้า privacy policy / cookie consent ถ้าเก็บข้อมูลส่วนบุคคลหรือใช้ tracking (แจ้งลูกค้าให้ตรวจกับผู้เชี่ยวชาญ PDPA — ผู้ทดสอบไม่ให้คำปรึกษากฎหมาย)
- [ ] ข้อความ ราคา เบอร์โทร อีเมลติดต่อ ถูกต้องตรงกับธุรกิจ
- [ ] SEO พื้นฐาน: title/description ไม่ซ้ำทุกหน้า, ไม่มี `noindex` ค้างบน production
