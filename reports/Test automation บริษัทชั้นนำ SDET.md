# บริษัทชั้นนำเปลี่ยนนักทดสอบเป็นวิศวกรสร้างระบบคุณภาพ

บริษัทเทคโนโลยีระดับโลกที่มีหลักฐานอ่านได้ลงทางเดียวกันว่า **"วิศวกรเป็นเจ้าของคุณภาพของโค้ดตัวเอง"** ส่วนบทบาท tester ที่เหลืออยู่ถูกนิยามใหม่เป็นวิศวกรที่สร้าง test infrastructure, เครื่องมือ CI และโค้ชทีม ไม่ใช่ผู้ตรวจรับงานปลายทาง: Microsoft ยุบตำแหน่ง SDET ราวปี 2014, Google เปลี่ยน SET เป็น SETI/EngProd, Atlassian เปลี่ยน QA เป็น "Quality Assistance" และ Netflix ให้ "full cycle developer" ทำงานแบบ SWE + SDET + SRE ในคนเดียว ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-microsoft-does-quality-assurance); [InfoQ, Netflix](https://www.infoq.com/news/2018/06/netflix-full-cycle-developers/); [InfoQ, Atlassian](https://www.infoq.com/news/2016/11/future-qa-atlassian)). สิ่งที่ SDET ออกแบบจริงคือชุดระบบที่ทำให้ผล test "เชื่อถือได้และเร็ว": test pyramid/honeycomb, framework หลายชั้น, การแยก flaky test ออกจาก pipeline อย่างมีเจ้าของ, release gate แบบ canary/one-box และ non-functional gate. ข้อควรระวังที่สำคัญคือ **มีเพียง Google เท่านั้นที่เผยสัดส่วนเชิงตัวเลขของ pyramid (ราว 80/15/5 โดยจำนวน test)** บริษัทอื่นที่ศึกษา (Microsoft, Spotify, Shopify, Atlassian ฯลฯ) ไม่เผยสัดส่วน และตัวเลข 70/20/10 ไม่มีแหล่งที่อ่านได้ในชุดโน้ตนี้. ด้าน AI เอกสารทางการ (Playwright, Meta, Google) ยืนยันตรงกันว่าการใช้งานจริงเป็น "AI สร้าง + กรองอัตโนมัติ + คนรีวิว" และงานที่ยังเป็นของมนุษย์คือการตัดสินว่า oracle ที่ถูกต้องคืออะไร. สำหรับประเทศไทย หลักฐานบางมาก: อ่านประกาศรับสมัครเต็มได้เพียง 2 ฉบับ (Playwright เป็นเครื่องมือที่ต้องการ/ที่พึงประสงค์ทั้งคู่) และหลักฐานสาธารณะที่แข็งที่สุดของ KBTG/SCB TechX คือประกาศเป็น ISTQB Platinum Partner. ข้อเสนอสำหรับหลักสูตร Playwright/Postman/CI อยู่ในหัวข้อ "ข้อเสนอสำหรับหลักสูตร" และตารางระดับหลักฐานอยู่ท้ายรายงาน.

**วิธีอ่านป้ายกำกับระดับหลักฐาน** ในรายงานนี้ **[V]** = ผู้วิจัยเปิดอ่านหน้า/เอกสารจริงในเซสชัน (แต่เครื่องมือ WebFetch คืนสรุปจากโมเดล ไม่ใช่ข้อความดิบ จึงควรตรวจคำพูดตรงกับต้นฉบับก่อนยกเป็นข้อความอ้างในเนื้อหาคอร์ส), **[S]** = แหล่งรอง/อ่านได้เพียงบางส่วน (mirror, ความเห็นผู้อ่าน), **[U]** = ไม่ยืนยัน (เห็นเฉพาะ search snippet หรือเปิดไม่ได้ เช่น 403/404), **[I]** = ข้อสรุปของผู้เขียนโน้ตหรือของรายงานนี้ ไม่ใช่คำกล่าวของแหล่งที่มา. ข้อความที่ไม่มี URL ในโน้ตถูกตัดออกจากรายงานนี้.

## บทบาทเปลี่ยนจาก "ผู้ตรวจงาน" เป็นวิศวกรโครงสร้างพื้นฐานด้านคุณภาพ

**Google.** หนังสือ Software Engineering at Google ระบุว่าวิศวกรเขียนและรัน automated test ของโค้ดตัวเอง ทุก code change ต้องผ่าน review และ reviewer บล็อกได้หากไม่มี test; test infrastructure ถูกมองเป็นผลิตภัณฑ์ที่ "ต้องมี test ของตัวเองเสมอ" ([SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html), [ch. 12](https://abseil.io/resources/swe-book/html/ch12.html)) **[V]**. Google ไม่ได้ใช้การบังคับ แต่ใช้กลไกวัฒนธรรม: orientation สอนการทดสอบ, โปรแกรม "Test Certified" 5 ระดับที่ช่วยกว่า 1,500 โปรเจกต์ และถูกแทนในปี 2015 ด้วยคะแนน Project Health (pH) 1-5 แบบอัตโนมัติ ([SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)) **[V]**. ส่วนรายละเอียดการเปลี่ยน SET เป็น SETI (Software Engineer, Tools & Infrastructure) ในโพสต์ "From QA to Engineering Productivity" (2016) มาจากความเห็นและคำตอบของผู้เขียนที่มองเห็นในหน้า เพราะเนื้อโพสต์ไม่ถูกแสดง: SETI เน้น automation/build/release/metrics ส่วน Test Engineer เน้น test plan, risk และ exploratory testing แต่ยังมีเกณฑ์การเขียนโค้ด ([Google Testing Blog](https://testing.googleblog.com/2016/03/from-qa-to-engineering-productivity.html)) **[S]**. หน้า careers ของ Google EngProd เห็นเพียง snippet **[U]**.

**Microsoft.** บทความของ Gergely Orosz (2023) ระบุว่าอัตราส่วน SDE:SDET 2:1 เป็นเรื่องปกติจนถึงราวปี 2014 (ตัวอย่าง Skype for Xbox One ปี 2012: 12 SDE, 6 SDET) แล้วทีม web ที่ ship รายวันค่อย ๆ รวมบทบาท ก่อน Microsoft ยกเลิกตำแหน่ง SDET อย่างเป็นทางการกลางปี 2014 และใช้ชื่อ "SE" ให้ทุกคน โดยเหตุผลที่ระบุคือจังหวะ release ที่เร็ว การโยนงานไปมาระหว่าง dev-test และ feedback ที่ช้า; Orosz เองระบุว่าเป็นการประเมินไม่ใช่ข้อมูลเชิงสถิติ ([Pragmatic Engineer](https://newsletter.pragmaticengineer.com/p/how-microsoft-does-quality-assurance)) **[S]** — เป็นแหล่งรองเดียวที่ไม่มีประกาศทางการของ Microsoft มายืนยัน. หลักฐานปฐมภูมิที่หนุนบางส่วนคือ Brian Harry (2017) ที่เขียนว่าทีม VSTS รวมองค์กร dev กับ test, ลบเส้นแบ่งผู้เขียนโค้ด/ผู้ทดสอบ และทุกคนรับผิดชอบคุณภาพงานตัวเอง ([Brian Harry](https://devblogs.microsoft.com/bharry/testing-in-a-cloud-delivery-cadence/)) **[V]**.

**Meta และ Amazon.** โน้ตไม่พบแหล่งปฐมภูมิที่นิยามตำแหน่ง tester/SDET ของ Meta; สิ่งที่อ่านได้คือ central release engineering ผลักการเปลี่ยนแปลงที่ผ่าน automated test ให้พนักงานก่อน แล้ว 2% ของ production แล้ว 100% ([Meta Engineering, 2017](https://engineering.fb.com/2017/08/31/web/rapid-release-at-massive-scale/)) และ Sapienz ที่ Meta ยอมรับว่าวิศวกรยังออกแบบบาง test ได้ดีกว่าเครื่องมือเพราะรู้โดเมน ([Meta Engineering, 2018](https://engineering.fb.com/2018/05/02/developer-tools/sapienz-intelligent-automated-software-testing-at-scale/)) **[V]**. Amazon: AWS Builders' Library ระบุว่า "การเป็นเจ้าของผลิตภัณฑ์หมายถึงการเป็นเจ้าของผลของ defect ด้วย" ทีมเล็กรับ production issue เอง ([Mansour, 2019](https://builder.aws.com/content/3F08Mhh186qOa4VhG19egs06NJa/going-faster-with-continuous-delivery)) **[V]**; ข้อกำหนด SDET ของ Amazon (OO language, สร้าง test framework, CI/CD, debug) มาจากสรุปผลค้นหาเท่านั้น เพราะหน้า job คืน 404 ([amazon.jobs](https://amazon.jobs/en/jobs/2904059/software-development-engineer-in-test-2025-us)) **[U]**, และคำว่า "two-pizza" ไม่พบในแหล่ง Amazon ใดที่อ่านได้ จึงไม่ควรอ้าง.

**Netflix, Atlassian, Shopify, Uber.** InfoQ (2018) รายงานโมเดล Full Cycle Developers ของ Netflix: นักพัฒนาเป็นเจ้าของการ operate บริการที่ตนสร้าง "คิดและทำเหมือน" SWE, SDET และ SRE โดยทีมกลาง (Cloud Platform, Performance & Reliability, Engineering Tools) ให้ "Paved Road"; ผู้เขียนเตือนเรื่อง overhead และ burnout และแนะให้ใช้ "ความซับซ้อนเท่าที่จำเป็น" ([InfoQ](https://www.infoq.com/news/2018/06/netflix-full-cycle-developers/)) **[V]** (โพสต์ต้นฉบับของ Netflix เปิดไม่ได้ **[U]**). Atlassian (2016) ยืนยันว่าไม่ได้ยุบ QA แต่ย้ายจากการทดสอบเองไปเสริมให้นักพัฒนาสร้างคุณภาพได้เอง และ QA ไม่ควรเป็น "gatekeeper" ([InfoQ](https://www.infoq.com/news/2016/11/future-qa-atlassian)); บล็อกปี 2017 ระบุ 6 ทักษะของ Quality Assistance engineer ได้แก่ influence, testing expertise, teaching, inspiration, facilitation และ identifying problems ([Atlassian](https://www.atlassian.com/blog/development/6-essential-skills-quality-assistance-engineer)) **[V]**. Shopify มีทีม Test Infrastructure เฉพาะที่ดูแลความเร็ว CI และ flaky test ของ monolith ([Shopify Engineering](https://shopify.engineering/faster-shopify-ci)) และ Uber ให้ platform team เป็นเจ้าของ "realm" ของ test แต่ละประเภท ตั๋วของ test ที่ไม่แข็งแรงส่งไปทีมเจ้าของ ([Uber](https://www.uber.com/blog/flaky-tests-overhaul/)) **[V]**. บทความ Pragmatic Engineer ที่อ้างว่า Big Tech ส่วนใหญ่ไม่มีตำแหน่ง SDET/QA เฉพาะ อ่านได้เพียงพาดหัว (paywall) **[U]**.

**ข้อสรุป [I]:** รูปแบบร่วมคือสองทางเลือก — (ก) วิศวกรฝังทีมที่สร้าง framework/tooling (Google SETI, Amazon SDET, Shopify/Uber test infra) หรือ (ข) ไม่มีตำแหน่งแยกเลย (Microsoft SE, Netflix). การยุบตำแหน่งสัมพันธ์กับ cadence ที่เร็วขึ้นมากกว่าต้นทุนเพียงอย่างเดียว (Orosz เองอ้างทั้ง cadence และการปลดพนักงาน) และแหล่งของ Netflix/Atlassian เป็นปี 2016-2018 จึงยังไม่ยืนยันว่าผังองค์กรปัจจุบันตรงกัน. ผู้เรียนระดับต้นควรคาดหวังบทบาท "วิศวกรที่เชี่ยวชาญด้าน test tooling และ automation" ไม่ใช่ผู้รัน test case ด้วยมือ.

## สิ่งที่ต้องรู้ มุมคิด บันไดอาชีพ และวันทำงานจริง

**ความรู้และมุมคิด.** ISTQB CTFL v4.0.1 (ฉบับ errata ลงวันที่ 15 กันยายน 2024) ระบุทักษะของ tester ได้แก่ ความรู้ด้านการทดสอบ, ความละเอียด/ความอยากรู้/ใส่ใจรายละเอียด, การสื่อสารและฟังอย่างตั้งใจ, การคิดวิเคราะห์เชิงวิพากษ์และความคิดสร้างสรรค์, ความรู้เทคนิค และความรู้โดเมน และเตือนว่า tester มัก "เป็นผู้นำข่าวร้าย" ซึ่ง confirmation bias ทำให้ผู้ฟังรับข้อมูลที่ขัดกับความเชื่อได้ยาก จึงต้องสื่อสาร defect อย่างสร้างสรรค์ ([CTFL v4.0.1](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf), หัวข้อ 1.5.1) **[V]**. แนวคิด whole-team approach (ทุกคนรับผิดชอบคุณภาพ) มาพร้อมรายการข้อเสียของการขาด independence เช่น ความสัมพันธ์แบบเป็นปฏิปักษ์ และการที่ tester ถูกมองเป็นคอขวด ([CTFL v4.0.1](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf), 1.5.2-1.5.3) **[V]**. ฝั่ง automation, CTAL-TAE v2.0 (GA 3 พฤษภาคม 2024) วางหลักว่า "test automation is a software development activity" โดยคาดหวังทักษะ software engineering (OOP, SOLID) และชี้ design pattern 3 ตัวที่สำคัญที่สุดสำหรับ TAE คือ facade, singleton และ page object model ([CTAL-TAE v2.0](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf), 3.1.5) **[V]**. เทคนิคออกแบบ test ที่ใช้ตัดสินว่าจะ automate อะไรคือ equivalence partitioning, boundary value analysis (2-value และ 3-value), decision table และ state transition ซึ่ง CTFL ให้นิยาม coverage ที่คำนวณได้ ([CTFL v4.0.1](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf), บทที่ 4) **[V]**.

**ข้อผิดพลาดที่พบบ่อยของ automation ระดับต้น.** ไม่มีงานวิจัยที่นับความถี่ข้อผิดพลาดของผู้เริ่มต้นในชุดโน้ต รายการนี้ประกอบจาก syllabus และบทความผู้ปฏิบัติ **[I]** แต่แต่ละข้อมีแหล่งรองรับ: ใช้ hard-coded wait ซึ่ง TAE เรียกว่า "root cause ของ defect ใน test automation จำนวนมาก" (ควรใช้ polling+timeout หรือ event) ([CTAL-TAE v2.0](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf), 8.1.2); พึ่ง capture/playback เกินกว่าระบบเล็กที่แทบไม่เปลี่ยน; กระจาย locator ไว้ในทุก test แทนที่จะรวมใน page model; ฮาร์ดโค้ดข้อมูลและรหัสผ่านในสคริปต์; ทิ้ง flaky test ไว้ใน suite หลักจนทีมเลิกสนใจผลแดง ([Fowler](https://martinfowler.com/articles/nonDeterminism.html)); และสร้าง "ice-cream cone" ที่มี E2E เป็นส่วนใหญ่ ([Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)) **[V]**.

**บันไดอาชีพ.** ไม่มีบันไดมาตรฐานข้ามอุตสาหกรรม สิ่งที่ยืนยันได้คือเส้นทางใน syllabus ของ ISTQB (Foundation, Core Advanced: Test Analyst/Technical Test Analyst/Test Manager, Expert และสาย Agile/Specialist) ([CTFL v4.0.1](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf), หน้า 10) **[V]**. กรอบของ GitLab (Associate, Intermediate, Senior, Staff, Principal) ([GitLab handbook](https://handbook.gitlab.com/handbook/engineering/careers/matrix/quality/software-engineer-in-test)), ตำแหน่ง IC1-IC7/M3-M7 ของ Dropbox และเส้นทาง Tester → SDET → Test Manager ของ Construx ([Construx](https://www.construx.com/?p=2089)) อ่านเนื้อหาไม่ได้ จึงเป็น **[U]** ทั้งหมด. ตารางความสามารถรายระดับ (Manual QA → Automation engineer → SDET → Senior/Staff/Test architect → QA lead/QE manager) ในโน้ตเป็นการสังเคราะห์ของผู้วิจัย **[I]** โดยมีข้อสังเกตหลักว่า "การเลื่อนจาก tester เป็น SDET ส่วนใหญ่คือการเพิ่มวิธีปฏิบัติด้านวิศวกรรม (design, code review, CI, observability) มากกว่าทฤษฎีการทดสอบใหม่" และชื่อตำแหน่งไม่เป็นมาตรฐาน จึงควรสอนเป็น capability. ด้านค่าตอบแทน PractiTest 2026 (self-reported, correlation เท่านั้น) รายงาน premium ของทักษะการสื่อสาร +36.1% และ critical thinking +7.7% ส่วน API testing -5.7% และ programming -0.1%; สำหรับคนประสบการณ์ 10 ปีขึ้นไป ทักษะ leadership/strategy สัมพันธ์กับรายได้ +10.6% ขณะที่ technical execution -13.8% ([PractiTest](https://www.practitest.com/state-of-testing/)) **[V]** — ตัวเลขนี้อธิบายความสัมพันธ์ ไม่ได้บอกให้เลิกเรียนโค้ด เพราะงานรีวิวผลของ AI ยังต้องเขียน test เองเป็น **[I]**.

**วันทำงานจริง.** ภาพรวมที่แหล่งอ่านได้ยืนยันคือ: (1) ช่วง planning, tester เขียน user story/acceptance criteria ที่ทดสอบได้, ร่วมวิเคราะห์ risk, แตกงานทดสอบ และประเมินเวลา ([CTFL v4.0.1](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf), 5.1.2); (2) ใน Three Amigos (PO, tester, developer) tester "สร้างสถานการณ์และ edge case จำนวนมากโดยถามว่าแอปจะพังได้อย่างไร" ([Cucumber: Who does what](https://cucumber.io/docs/bdd/who-does-what/)); (3) เขียนและรีวิว test ที่ระดับต่ำสุดที่ทำได้ และเมื่อ test ระดับสูงพบบั๊กที่ระดับล่างไม่เจอให้เพิ่ม test ระดับล่าง ([Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)); (4) triage CI failure ตามขั้นตอน 5 ข้อของ TAE: เคยเกิดมาก่อนหรือไม่, ระบุ test case, หา step ที่ล้ม, วิเคราะห์สถานะ SUT จาก screenshot/API/network log, หาก SUT ผิดจึงเปิด defect พร้อม log โดยสถานะผลต้องแยก passed / failed / "TAS failure" ([CTAL-TAE v2.0](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf), 6.1); (5) เขียน defect report ที่มี environment, ขั้นตอนทำซ้ำ, expected vs actual, severity/priority ([CTFL v4.0.1](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf), 5.5); (6) exploratory testing แบบมี charter และ debrief ([CTFL v4.0.1](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf), 4.4.2) **[V]**. เรื่องตัวชี้วัด: ISTQB นิยามเฉพาะ defect density และ defect detection percentage ไม่นิยาม "flaky rate", "defect escape rate" หรือ MTTR และ DORA (อัปเดต 5 มกราคม 2026) ให้ 5 ตัวชี้วัดการส่งมอบ ได้แก่ change lead time, deployment frequency, failed deployment recovery time, change fail rate, deployment rework rate พร้อมคำเตือนว่าไม่ควรใช้เป็นเป้าหมายหรือเทียบข้ามแอป ([DORA](https://dora.dev/guides/dora-metrics/)) **[V]**; สูตร escape rate/flaky rate ที่สอนในคอร์สจึงเป็นนิยามของคอร์สเอง ต้องระบุ window และแหล่งข้อมูลเสมอ **[I]**.

## รูปทรง pyramid มีหลายแบบ แต่มีเพียง Google ที่เผยสัดส่วน

**Google: ขนาดและสัดส่วนคนละเรื่องกับ scope.** Google แบ่ง test ตาม "size" (small = process เดียว ห้าม sleep/I-O/network; medium = หลาย process แต่ network จำกัดที่ localhost; large = หลายเครื่อง) แยกจาก "scope" (unit/integration/E2E) และให้เป้าคร่าว ๆ **ราว 80% unit, 15% integration, 5% E2E ตามจำนวน test** พร้อม antipattern "ice cream cone" และ "hourglass" ([SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)) **[V]**. กฎ Beyoncé ("ถ้าคุณชอบมัน ก็ควรใส่ test ให้มัน") ครอบคลุมทั้ง performance, accessibility, security และ failure handling; ตัวอย่างเกณฑ์ coverage 80% มาพร้อมคำเตือนว่าทีมมักมองขั้นต่ำเป็นเพดาน และ coverage บอกเพียงว่าบรรทัดถูกรัน ไม่ได้บอกว่าถูกตรวจ ([SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)) **[V]**. แนวเขียน test ได้แก่ test ผ่าน public API, ตั้งชื่อตามพฤติกรรม, ไม่มี loop/if ใน test, DAMP มากกว่า DRY, และชอบ real implementation → fake → stub ตามลำดับ เพราะ mocking เกินจำเป็นทำให้ test แพงและจับบั๊กได้น้อย ([ch. 12](https://abseil.io/resources/swe-book/html/ch12.html), [ch. 13](https://abseil.io/resources/swe-book/html/ch13.html)) **[V]**.

**บริษัทอื่น: รูปทรงโดยไม่มีตัวเลข.** Microsoft Playbook ครอบคลุม test ทุกประเภท (unit, integration, E2E ที่มี recipe ของ Postman, consumer-driven contract, performance, smoke, synthetic monitoring, UI รวม accessibility, fault injection) แต่ไม่ระบุ pyramid หรือสัดส่วน ([Playbook](https://microsoft.github.io/code-with-engineering-playbook/automated-testing/)) **[V]** ส่วน Microsoft Learn แนะนำ "เขียน test ที่ระดับต่ำสุดเท่าที่ทำได้" และไม่สนับสนุน UI test เพราะไม่น่าเชื่อถือ ([Microsoft Learn](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable)) **[V]**. Spotify เสนอ **honeycomb** สำหรับ microservice: เน้น Integration Tests ของ service เดี่ยวผ่านจุดปฏิสัมพันธ์ มี Implementation Detail Tests น้อย และ Integrated Tests (ผลขึ้นกับความถูกต้องของระบบอื่น) ให้น้อยที่สุดหรือไม่มี โดยยอมรับ trade-off ว่า test ใช้เวลาเป็นวินาทีและให้ feedback ไม่แม่นเท่า ([Spotify Engineering](https://engineering.atspotify.com/2018/01/testing-of-microservices/)) **[V]**; Fowler/Vocke ย้ำ "ยิ่งระดับสูงยิ่งน้อย" และ "push tests down" โดยไม่มีสัดส่วน ([Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)) **[V]**; testing trophy ของ Kent C. Dodds เพิ่มชั้น Static และบทความไม่ได้ระบุขนาดของแต่ละชั้น ([Dodds](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)) **[V]**. Shopify ให้บทเรียนเรื่องความไว้ใจ: "pyramid ใช้ได้ดีตราบที่ suite น่าเชื่อถือ" ชุด mobile E2E ถูกดึงออกจาก PR check เพราะบล็อก PR ดีมากกว่า PR เสีย หลังเขียนใหม่ความเสถียรจาก 50% เป็น 98% และ test ใหม่ต้องผ่านการรันซ้ำก่อนเข้า suite ที่บล็อก ([Shopify Engineering](https://shopify.engineering/mobile-e2e-testing)) **[V]**. **ตัวเลข 70/20/10 ที่มักอ้างถึง Google ไม่มีในแหล่งที่อ่านได้ (โน้ตระบุว่ายังไม่ยืนยัน) จึงไม่ควรกล่าวว่าบริษัทใดใช้ [U]; อย่าเปลี่ยนตัวเลข 80/15/5 ของ Google ให้เป็นมาตรฐานอุตสาหกรรม** ([Google ระบุเป็น "rough"](https://abseil.io/resources/swe-book/html/ch11.html)). ข้อสรุป [I]: pyramid เหมาะ monolith/logic หนัก (Shopify Core), honeycomb เหมาะ microservice, trophy เหมาะ front-end JavaScript และทั้งสามเป็น heuristic ไม่ใช่มาตรฐาน.

**สถาปัตยกรรม framework.** TAE v2.0 นิยาม gTAA เป็นภาพนามธรรมของการเชื่อมต่อ ได้แก่ interface ไปยัง SUT, project management, test management, configuration management และ 4 ความสามารถคือ test generation (ไม่บังคับ), definition, execution, adaptation พร้อมโครงสร้าง TAF 3 ชั้น: test scripts → business logic → core libraries โดย "ห้าม test script เรียก core library ตรง" และให้ "จำนวนชั้นน้อยไว้" ([CTAL-TAE v2.0](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf), 3.1) **[V]**. Playwright ให้ชิ้นส่วนที่ตรงกับโครงนี้: fixtures (setup/teardown, test-scoped/worker-scoped/auto), page object (ลดการซ้ำของ locator) ซึ่งเอกสารปฏิบัติเป็นส่วนเสริมกัน, `APIRequestContext` สำหรับ API test และสร้างข้อมูลล่วงหน้า, project dependencies (แนะนำแทน `globalSetup` เพราะปรากฏใน HTML report, มี trace และ retry) และ config ที่ขับด้วย env ([Fixtures](https://playwright.dev/docs/test-fixtures), [POM](https://playwright.dev/docs/pom), [API testing](https://playwright.dev/docs/api-testing), [Global setup](https://playwright.dev/docs/test-global-setup-teardown)) **[V]**. แนวทางหลักของ Playwright คือทดสอบพฤติกรรมที่ผู้ใช้เห็น ใช้ locator แบบ role/text/test-id, web-first assertion ที่ retry เอง, และ test ต้องแยกจากกัน ([Best Practices](https://playwright.dev/docs/best-practices)) **[V]**. โครงโฟลเดอร์ `tests/ → pages/ → fixtures/ → api/ → data/ → config/` ที่โน้ตเสนอเป็นการแมปของผู้วิจัยกับฟีเจอร์ที่เอกสารมี ไม่ใช่มาตรฐานทางการ **[I]**.

**Test data, environment, secrets.** ลำดับของแนวทางที่รองรับโดยแหล่ง: สร้างข้อมูลต่อ test ผ่าน API ด้วยค่าที่ไม่ซ้ำ แล้วลบ; ใช้บัญชี/ข้อมูลต่อ worker ด้วย worker-scoped fixture (เช่น `workerIndex`); ใช้ named lock สำหรับทรัพยากรที่ต้องแชร์; ใช้ serial mode เป็นทางสุดท้ายเพราะเอกสารไม่สนับสนุน ([Parallelism](https://playwright.dev/docs/test-parallel)) **[V]**. Fowler ชี้ว่าต้นตอ non-determinism คือ shared state, async, remote service, เวลา และ resource leak พร้อมวิธีแก้ (rebuild state, ห่อ clock, test double + contract test เป็นระยะ) ([Fowler](https://martinfowler.com/articles/nonDeterminism.html)) **[V]**. Testcontainers เสนอใช้ dependency จริงใน container ที่ทิ้งได้แทน mock ([Testcontainers](https://testcontainers.com/guides/getting-started-with-testcontainers-for-nodejs/)) **[V]**. เรื่อง secrets: ไฟล์ `storageState` อาจมี cookie/header ที่ปลอมตัวได้ จึงห้าม commit ([Authentication](https://playwright.dev/docs/auth)); GitHub แนะนำ least privilege, ตั้ง `GITHUB_TOKEN` เป็น read-only, ใช้ OIDC แทน credential อายุยาว และ pin third-party action ด้วย commit SHA ([GitHub Docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)) **[V]**. **ช่องว่างสำคัญ:** โน้ตไม่ได้อ่านแหล่งใดเรื่อง data masking/anonymisation, synthetic data generator, หรือข้อกำหนด PDPA/ธนาคารแห่งประเทศไทยด้าน test data; ประโยค "test data ห้ามใช้ PII ลูกค้าจริง" อ้างได้จากหลักการ PDPA ทั่วไปเท่านั้น และห้ามกล่าวว่า BOT หรือ PDPA มี clause เฉพาะเรื่องนี้จนกว่าจะอ่านต้นฉบับ ([BOT IT risk](https://www.bot.or.th/th/our-roles/payment-systems/information-technology-risk-supervision.html) ไม่กล่าวถึง test data) **[V สำหรับการไม่กล่าวถึง]**.

## Flaky test: ตรวจจับ กักกัน ติดตามเจ้าของ แล้วแก้ที่ต้นเหตุ

**ขนาดของปัญหา.** ตัวเลขจากโพสต์ของ John Micco (2016) คือราว 1.5% ของการรัน test ทั้งหมดให้ผล flaky, เกือบ 16% ของ test มีความ flaky บ้าง และราว 84% ของการเปลี่ยนจาก pass เป็น fail ในการทดสอบหลัง submit เกี่ยวข้องกับ test ที่ flaky — แต่ **ตัวเลขเหล่านี้อ่านจาก mirror (googledirectorynews.blogspot.com) เพราะเนื้อโพสต์ต้นฉบับไม่แสดง จึงเป็นแหล่งรอง [S]** ([ต้นฉบับ](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html); [mirror](https://googledirectorynews.blogspot.com/2016/05/flaky-tests-at-google-and-how-we.html)). หนังสือของ Google พูดถึงอัตรา "ราว 0.15%" ที่ยังเท่ากับ flaky หลายพันครั้งต่อวัน และ test เสียคุณค่าเมื่อ flakiness ใกล้ 1% ([SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)) **[V]** — สองตัวเลข (1.5% ของการรัน กับ ~0.15%) มาจากคนละยุคและตัวหาร โน้ตระบุว่าแหล่งไม่ได้ปรับให้ตรงกัน จึงห้ามเทียบหรือเฉลี่ย. ตัวเลข 0.5%/1.6%/14% ตามขนาด test และ "when in doubt, doubt the tests first" เห็นเพียง search summary **[U]**. Atlassian รายงานว่า flaky test ทำให้ master build ของ Jira Frontend ล้มสูงสุด 21% และราว 15% ของ Jira backend สูญเสียเวลานักพัฒนากว่า 150,000 ชั่วโมงต่อปี ([Atlassian, ธ.ค. 2025](https://www.atlassian.com/blog/atlassian-engineering/taming-test-flakiness-how-we-built-a-scalable-tool-to-detect-and-manage-flaky-tests)) **[V]**.

**ขั้นบันไดของการจัดการ.** แหล่งที่อ่านได้ลู่เข้าหาลำดับเดียวกัน (สรุปเป็นขั้นโดยผู้วิจัย **[I]**): (1) ตรวจจับด้วย retry ใน build เดียวกัน — Atlassian Flakinator รันซ้ำ test ที่ล้มและหยุดเมื่อผลพลิกครั้งแรก ตรวจพบ 81% ในบางผลิตภัณฑ์; (2) ให้คะแนนจากประวัติ — Atlassian ใช้คะแนน Bayesian 0-1 บน moving window ส่วน Uber ใช้ state machine (new/stable/unstable/disabled/deleted) ที่ test ต้องผ่านต่อเนื่อง N ครั้งจึงกลับเป็น stable; (3) กักกัน (quarantine) โดยยังรันและติดตามแบบไม่บล็อก; (4) เปิด ticket ถึงทีมเจ้าของพร้อม due date ([Atlassian](https://www.atlassian.com/blog/atlassian-engineering/taming-test-flakiness-how-we-built-a-scalable-tool-to-detect-and-manage-flaky-tests), [Uber](https://www.uber.com/blog/flaky-tests-overhaul/)) **[V]**. Microsoft VSTS ปิด test ที่ล้มใน reliability run อัตโนมัติและเปิด bug แล้วเปิดใช้ใหม่เมื่อ bug ปิด: sprint 116-119 พบ 170 reliability bug แก้เฉลี่ย 3.75 วัน และบางส่วนเป็น race condition ของผลิตภัณฑ์จริง ([Brian Harry](https://devblogs.microsoft.com/bharry/testing-in-a-cloud-delivery-cadence/)) **[V]**. TAE ก็ให้ย้าย test ที่ผลไม่น่าเชื่อถือออกจาก suite ที่รันจริงเพื่อวิเคราะห์แยก ([CTAL-TAE v2.0](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf), 7.1.2) และ DORA ระบุว่า "flaky tests should not be tolerated" โดยต้องได้ผลภายในไม่ถึงสิบนาที ([DORA](https://dora.dev/capabilities/test-automation/)) **[V]**.

**Retry ช่วยตรวจจับ ไม่ใช่การแก้.** Shopify คำนวณว่าหาก test แต่ละตัวผ่านอย่างอิสระที่ 99.95% pipeline 100 test จะผ่านราว 95% และ 20 pipeline เหลือราว 35% การ retry ได้ถึง 3 ครั้งยกอัตราผ่านของ Android จากราว 31% เป็นเกือบ 90% และ iOS 67% เป็น 97% แต่ก็เตือนว่าทำให้ CI ช้าลงและซ่อนปัญหาความน่าเชื่อถือ ([Shopify Engineering](https://shopify.engineering/unreasonable-effectiveness-test-retries-android-monorepo-case-study)) **[V]**. Google เองเตือนว่าการ quarantine อาจกลบ race condition จริง และทีมหนึ่งพบว่าเมื่อ test ที่เคยเสถียรเริ่ม flaky แล้วย้อนถึง code change ได้ ต้นเหตุคือบั๊กใน production ราวหนึ่งในหก (มาจากความเห็นผู้เขียน ไม่ใช่เนื้อโพสต์ **[S]**) ([Google Testing Blog, 2017](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html)). Playwright รายงานผลแบบ "flaky" (ล้มครั้งแรก ผ่านเมื่อ retry) แยกจาก passed/failed, ปิด retry เป็นค่าเริ่มต้น และแนะนำ `trace: 'on-first-retry'` ([Test retries](https://playwright.dev/docs/test-retries), [Trace Viewer](https://playwright.dev/docs/trace-viewer-intro)) **[V]**.

**CI ที่ขนาดใหญ่: ลดงานก่อนเพิ่มเครื่อง.** Shopify Core มีมากกว่า 170,000 test และใช้ราว 41 ชั่วโมงถ้ารันบนเครื่องเดียว การเลือก test ตามการเปลี่ยนแปลงทำให้ไม่ต้องรันทั้งหมดใน 45% แล้วเกิน 60% ของ build; p95 ของ CI ลดจากราว 45 เหลือ 18 นาที และ 68% ของเวลา CI เป็น overhead ก่อนรัน test ([Shopify Engineering](https://shopify.engineering/faster-shopify-ci)) **[V]**. Uber ตรวจ 2,500+ diff ต่อวันที่เฉลี่ย 10,000+ test ต่อ diff ([Uber](https://www.uber.com/blog/flaky-tests-overhaul/)) **[V]** ส่วนตัวเลขของ SubmitQueue (ลดทรัพยากร CI ราว 53%) และรายละเอียด Airbnb (Buildkite/Spinnaker, Flank) เป็น **[U]** เพราะอ่านไม่ได้. Google รัน monorepo >2 พันล้านบรรทัดและ test หลายพันล้านเคสต่อสัปดาห์ ([SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)); Meta รัน Android build 50,000-60,000 ครั้งต่อวัน ([Meta Engineering](https://engineering.fb.com/2017/08/31/web/rapid-release-at-massive-scale/)) **[V]**. สำหรับหลักสูตร ตัวเลขระดับนี้ใช้เพื่อชี้ว่า "ปัญหาเปลี่ยนรูปที่ขนาด" ไม่ใช่เป้าให้ผู้เรียนเลียนแบบ — Netflix เองเตือนไม่ให้ลอกแบบ "software unicorns" ([InfoQ](https://www.infoq.com/news/2018/06/netflix-full-cycle-developers/)).

**Pipeline ถึง production: test strategy รวม release gate.** Amazon วางด่านก่อนผลิต (alpha/beta, gamma, zeta), one-box (ไม่เกินราว 10% ของคำขอในหนึ่ง Region/AZ), rolling deploy ครั้งละไม่เกิน 33% ของ box, wave ข้าม Region, bake time อย่างน้อย 1 ชั่วโมงหลัง one-box และอย่างน้อย 12 ชั่วโมงหลัง regional wave แรก พร้อม auto-rollback จาก alarm; synthetic test รันอย่างน้อยทุกนาที ([Liguori, 2020](https://builder.aws.com/content/3ErTKQOTKc5NIw031UePBPxTQ6I/automating-safe-hands-off-deployments); [Mansour, 2019](https://builder.aws.com/content/3F08Mhh186qOa4VhG19egs06NJa/going-faster-with-continuous-delivery)) **[V]**. Meta ปล่อยเป็นชั้น (พนักงาน → 2% → 100%) พร้อม Gatekeeper feature flag ([Meta Engineering](https://engineering.fb.com/2017/08/31/web/rapid-release-at-massive-scale/)). Kayenta (Google/Netflix) เปรียบ canary กับ baseline ที่ deploy ใหม่ ให้คะแนน 0-100 ต่อ metric แล้ว rollback เมื่อ fail โดย Greg Burrell ของ Netflix กล่าวว่า automated canary analysis เป็นส่วนจำเป็นของการ deploy ที่ Netflix ([Google Cloud Blog](https://cloud.google.com/blog/products/gcp/introducing-kayenta-an-open-automated-canary-analysis-tool-from-google-and-netflix)) **[V]**; รายละเอียด ChAP ของ Netflix (canary ~1% ของ cluster เดิม) เป็น **[U]**. หลัก chaos engineering ที่อ่านได้: สมมติฐานบน steady-state metric, ลอง event จริง, ลด blast radius และรันอัตโนมัติต่อเนื่อง ([Principles of Chaos](https://principlesofchaos.org/)); Microsoft Learn ระบุ shift-right ว่าคือการทดสอบใน production ผ่าน tier rollout/feature flag/fault injection และจำกัด chaos ในสภาพแวดล้อมที่กระทบลูกค้าน้อย ([Shift right](https://learn.microsoft.com/devops/deliver/shift-right-test-production)) **[V]**. Feature flag เพิ่มสถานะที่ต้องตรวจ: Hodgson แนะให้ทดสอบ config ที่คาดว่าจะใช้จริง, fallback เมื่อปิด flag ใหม่ทั้งหมด และกำหนดวันถอด flag ([Fowler](https://martinfowler.com/articles/feature-toggles.html)) **[V]**. ข้ออ้างเรื่อง observability-driven development ของ Charity Majors เห็นเพียง snippet **[U]**.

## Contract, performance, accessibility และ security ต้องมีด่านที่วัดผลได้

**Contract testing.** Pact เป็นเครื่องมือ consumer-driven แบบ "contract by example": สัญญาเกิดขึ้นขณะรัน test ฝั่ง consumer และทดสอบเฉพาะส่วนของ provider ที่ consumer ใช้ เป้าหมายคือยืนยันว่าระบบทำงานร่วมกันโดยไม่ต้องพึ่ง integration test ที่แพงและเปราะ ([Pact docs](https://docs.pact.io/)); `can-i-deploy` ตรวจ Pact Matrix และคืน exit code 0/1 ก่อน deploy มี dry-run ให้ลอง ([Pact can-i-deploy](https://docs.pact.io/pact_broker/can_i_deploy)) **[V]**. TAE v2.0 ก็ระบุ contract testing ว่า "เกินกว่า schema validation" ทั้งแบบ consumer-driven และ provider-driven ([CTAL-TAE v2.0](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf), 5.1.3) **[V]**.

**Performance.** k6 แบ่งประเภทเป็น smoke, average-load, stress, soak, spike, breakpoint ([k6 test types](https://grafana.com/docs/k6/latest/testing-guides/test-types/)) และ `thresholds` แปลง SLO เป็นผ่าน/ไม่ผ่านด้วย exit code ไม่ใช่ศูนย์ เช่น `http_req_failed: ['rate<0.01']` ([k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)) **[V]**. JMeter ไม่ได้อยู่ในแหล่งที่อ่าน (แม้จะปรากฏในประกาศงานไทยตาม snippet **[U]**).

**Accessibility.** Playwright ใช้ `@axe-core/playwright` ตรวจ violation ด้วย tag `wcag2a/wcag2aa/wcag21a/wcag21aa` พร้อมคำเตือนในเอกสารว่า automated test ตรวจ WCAG violation ได้ไม่ครบและหลายปัญหาต้องทดสอบด้วยมือ โดยไม่ให้ตัวเลขเปอร์เซ็นต์ ([Playwright accessibility](https://playwright.dev/docs/accessibility-testing)) **[V]**; เอกสารไม่ระบุ tag ของ WCAG 2.2 ในข้อความที่อ่าน **[ไม่ยืนยัน]**. WCAG 2.2 เป็น W3C Recommendation ที่เผยแพร่ 12 ธันวาคม 2024 เพิ่ม 9 success criteria (เช่น Target Size (Minimum) 2.5.8, Accessible Authentication (Minimum) 3.3.8) และตัด 4.1.1 Parsing ([W3C](https://www.w3.org/TR/WCAG22/)) **[V, อ่านเพียงส่วนต้น]**. สองตัวเลขที่มักถูกนำมาเทียบกัน **ไม่ใช่ปริมาณเดียวกัน**: Deque รายงาน 57% ของ issue (นับตามปริมาณ จากข้อมูล 2,000+ audit, ~300,000 issue; เป็นการศึกษาของผู้ขายเครื่องมือเอง) ([Deque](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues)) กับ GOV.UK ปี 2017 ที่สร้างหน้าทดสอบ 143 ความบกพร่อง แล้วพบว่า 42 รายการ (29%) ไม่ถูกตรวจพบโดยเครื่องมือใดเลย และเครื่องมือเดี่ยวที่ดีที่สุดพบ 37-41% ([GOV.UK](https://accessibility.blog.gov.uk/2017/02/24/what-we-found-when-we-tested-tools-on-the-worlds-least-accessible-webpage/)) **[V; จำนวนเครื่องมือและเปอร์เซ็นต์ต้องตรวจซ้ำกับหน้าต้นฉบับก่อนยก]**. ข้อสรุปที่ปลอดภัย: automation จำเป็นแต่ไม่พอ และไม่ควรสรุปเป็นเปอร์เซ็นต์เดียว.

**Security.** ZAP Baseline Scan รันแบบ passive ไม่โจมตีเชิงรุก จึงออกแบบให้ใช้ใน CI/CD ได้ แม้กับเว็บ production; ค่าเริ่มต้นทุก alert เป็น WARN ปรับเป็น FAIL/IGNORE ผ่านไฟล์ config และมี exit code 0/1/2/3 ([ZAP](https://www.zaproxy.org/docs/docker/baseline-scan/)) **[V]**. OWASP Top 10:2025 มี A01 Broken Access Control ถึง A10 Mishandling of Exceptional Conditions ([OWASP](https://top10.owasp.org/2025)) **[V]**. **Postman/Newman:** เอกสาร Postman ระบุว่า Newman "จะไม่ได้รับการอัปเดตหรือแก้ไข" และแนะนำให้ใช้ Postman CLI ใน script/CI (ยังไม่ติดป้าย deprecated ในหน้า) พร้อมข้อจำกัด เช่น ไม่รองรับ OAuth 2.0 ใน Newman และใช้ `--bail` เพื่อ exit 1 เมื่อ test ล้ม ([Postman Learning Center](https://learning.postman.com/docs/collections/using-newman-cli/command-line-integration-with-newman/), [Postman CLI](https://learning.postman.com/docs/postman-cli/postman-cli-overview/)) **[V]**; การเทียบฟีเจอร์ Newman กับ Postman CLI อย่างครบถ้วนยังไม่ได้ตรวจ.

## AI-assisted testing: AI สร้างและซ่อม แต่คนต้องตัดสินว่า "ถูก" คืออะไร

**สิ่งที่มีเอกสารทางการ.** Playwright มี Test Agents สามตัว — planner (สำรวจแอปแล้วสร้างแผนเป็น Markdown จาก request, seed test และ PRD ถ้ามี), generator (แปลงแผนเป็น test และ "ตรวจ selector/assertion สดระหว่างทำ") และ healer (replay step ที่ล้ม ตรวจ UI หาองค์ประกอบเทียบเท่า เสนอ patch และรันซ้ำจนผ่านหรือถึง guardrail โดยจบที่ test ผ่านหรือถูก skip หากสรุปว่าฟังก์ชันพัง) ติดตั้งด้วย `npx playwright init-agents` และต้องสร้างนิยาม agent ใหม่เมื่ออัปเดต Playwright ([Playwright: Test agents](https://playwright.dev/docs/test-agents)) **[V]**. เอกสารไม่พูดถึงความแม่นยำ ต้นทุน หรือความไม่แน่นอน จึงไม่ควรอ้างความน่าเชื่อถือที่เอกสารไม่ได้อ้าง. Playwright MCP ทำงานจาก accessibility tree ไม่ใช่ภาพ และเอกสารเตือนว่า `browser_run_code_unsafe` เทียบเท่า RCE และข้อมูลเครื่องมือที่หน้าเว็บลงทะเบียนเป็น input ที่ไม่ไว้วางใจ ([Playwright MCP](https://playwright.dev/docs/getting-started-mcp)) **[V]**. ที่ Meta, TestGen-LLM (arXiv 2402.09171) ปรับปรุง unit test ที่มีอยู่ผ่าน filter ว่า build ได้, ผ่านอย่างเสถียร และเพิ่ม coverage: จาก Instagram Reels/Stories 75% build ได้ 57% ผ่านเสถียร 25% เพิ่ม coverage และใน test-a-thon วิศวกรรับข้อเสนอ 73% ([arXiv](https://arxiv.org/abs/2402.09171)); ACH ที่ใช้ mutation-guided สร้าง 571 test ด้านความเป็นส่วนตัว วิศวกรรับ 73% และ 36% เกี่ยวกับ privacy จริง ([arXiv 2501.12862](https://arxiv.org/abs/2501.12862), [Meta, ก.ย. 2025](https://engineering.fb.com/2025/09/30/security/llms-are-the-key-to-mutation-testing-and-better-compliance/)) **[V; เป็นผลของ Meta เอง ยังไม่มีผู้ทำซ้ำอิสระ]**. อีกงานของ Meta (TestGen แบบ observation-based, arXiv 2402.06111) รายงาน 518 test ที่ถูก land รัน 9,617,349 ครั้งใน CI และพบ fault 5,702 รายการ ([arXiv](https://arxiv.org/html/2402.06111v1)) **[V]**. ฝั่ง Google, Auto-Diagnose (arXiv 2604.12108) อ่าน log ของ integration test ที่ล้มแล้วสรุปสาเหตุใน Critique: ความถูกต้องของ root cause 90.14% จาก 71 กรณีที่ประเมินด้วยมือ ใช้กับ 52,635 test ที่ล้มและถูกให้ "Not helpful" 5.8% ([arXiv](https://arxiv.org/abs/2604.12108)) **[V]** — เป็นงาน "วินิจฉัย" ที่ความเสี่ยงต่ำกว่าการเขียน assertion; รายละเอียดว่าใช้ Gemini 2.5 Flash ที่ temperature 0.1 มาจากข่าวรอง **[U]**. ไม่พบโพสต์ปฐมภูมิของ Google Testing Blog เรื่อง AI test generation, และ FlowAgent/FlakyGuard เห็นเพียง snippet **[U]**.

**ข้อจำกัดที่มีหลักฐาน.** งานวิจัยบน 24 Java repository พบว่า oracle ที่ LLM สร้างส่วนใหญ่ "จับพฤติกรรมจริงของโปรแกรม" ทำให้หาบั๊กยาก ([arXiv 2410.21136](https://arxiv.org/abs/2410.21136)) **[V]**. พรีปรินต์ล่าสุด (ต.ค. 2026 ยังไม่ผ่าน peer review) บน 145 PR ของ SciPy, Qiskit และ pandas พบว่า 8%-17% ของ test ที่ AI สร้างเป็น fault-enforcing (ยืนยันพฤติกรรมที่ผิด) มีเพียง 2.4%-4.8% ที่ fault-revealing และ 83%-91% ของ fault-enforcing ยังผ่านต่อหลัง commit ถัดไป ([arXiv 2610.11835](https://arxiv.org/abs/2610.11835)) **[V]**. กรณีศึกษาเดี่ยวเรื่อง autonomous test repair (300 รายงาน) พบ convergence 70% ระดับ scenario-family, สำเร็จตั้งแต่ครั้งแรกเพียง 10% และพบการ "ซ่อม" โดยลด assertion หรือลบ test; ข้อสรุปคือ autonomy ที่ไม่มีข้อจำกัดให้ผลที่ทำให้เข้าใจผิด ([arXiv 2605.01471](https://arxiv.org/abs/2605.01471)) **[V]**. บทความ SD Times เรื่อง governance ของ self-healing ในธนาคารเป็นความเห็นพร้อมการจำลองที่ไม่มีเอกสารรองรับ จึงใช้เป็น checklist ได้แต่ไม่ใช่หลักฐานเชิงตัวเลข ([SD Times](https://sdtimes.com/software-testing/the-hidden-risk-in-self-healing-test-automation-a-governance-blueprint-for-digital-banking/)) **[V ในฐานะความเห็น]**.

**การยอมรับในอุตสาหกรรม: ตัวเลขจากประชากรต่างกัน ห้ามเฉลี่ย.** ตารางนี้วางผลสำรวจเคียงกันเพื่อให้เห็นนิยามและกลุ่มตัวอย่างที่ต่างกัน ไม่ได้มีไว้เทียบหรือรวมค่า:

ข้อสังเกตที่ปลอดภัยคือ "ส่วนใหญ่ทดลอง น้อยรายที่ฝังเข้ากระบวนการ" ซึ่งสอดคล้องกันระหว่าง WQR (15% ทั้งองค์กร) กับ PractiTest (ราว 85% อยู่ระดับ Initial/Experimenting) **[I]** แต่ทั้งคู่ไม่ใช่การเฉลี่ยหรือรวมค่ากัน. ไม่พบตัวเลขเฉพาะประเทศไทยหรือธนาคารอาเซียน.

**ทักษะที่หลักฐานชี้.** ไม่มีแหล่งวัด "ทักษะที่ทำให้ tester ยังมีงาน" ตรง ๆ ข้อสรุปมาจากหลักฐานทางอ้อม **[I]**: ใน deployment ที่มีเอกสารทุกกรณีมีขั้นตอนมนุษย์รีวิว (Meta: วิศวกร "ประเมิน test แทนที่จะต้องสร้าง"; Playwright: seed test และแผน Markdown เป็นจุดตรวจ) และความเสี่ยงหลักคือ test ที่ "เขียวแต่ไร้ความหมาย" จึงต้องการ test design และ risk analysis, การรีวิว assertion/diff ที่ healer แก้, พื้นฐาน framework ที่แน่นพอจะเขียนเองได้, ทักษะ CI/observability สำหรับ triage, การสื่อสาร และความปลอดภัยของข้อมูล/MCP; ส่วน "prompting" มีหลักฐานตรงอ่อนที่สุด. โน้ตไม่ได้ค้นเรื่อง Postman AI, AI ใน CI platform หรือเครื่องมือสร้าง test data ด้วย LLM และไม่ได้ค้นข้อกำหนดของ BOT ด้าน AI — ห้ามกล่าวข้อกำหนดนั้นโดยไม่มีแหล่ง.

## บทสรุป

สิ่งที่เปลี่ยนความเข้าใจมากที่สุดคือการเห็นว่า "test strategy" ในบริษัทชั้นนำกว้างกว่าชุด test: Amazon, Meta และ Netflix นับ canary, bake time, feature flag, synthetic probe และ auto-rollback เป็นส่วนหนึ่งของการทดสอบ ขณะที่ Shopify และ Atlassian วัดคุณค่าของ suite ด้วย "ความไว้ใจได้" (suite ที่บล็อก PR ดีมากกว่าเสียจะถูกดึงออก) ไม่ใช่จำนวน test หรือสัดส่วนรูปทรง. ผลคือสินค้าหลักของ SDET คือ feedback ที่เชื่อถือได้ภายในเวลาสั้น และหน่วยวัดที่ควรสอนคือ flaky ที่มองเห็น มีเจ้าของ และมีกำหนดแก้ ไม่ใช่เปอร์เซ็นต์ coverage หรือรูปทรง pyramid ที่ไม่มีแหล่งเผยตัวเลขนอกจาก Google.

ในยุค AI หลักฐานปัจจุบันบอกว่าต้นทุนของการ "เขียน test" ลดลง แต่ต้นทุนของการ "ตัดสินว่า test นั้นยืนยันสิ่งที่ถูกต้อง" ไม่ได้ลดตาม — test ที่ AI สร้างบนโค้ดที่มีบั๊กอาจล็อกบั๊กไว้เป็นรูปแบบ regression (8%-17% ในพรีปรินต์หนึ่งชุด ซึ่งยังต้องรอการยืนยันอิสระ) หลักสูตรที่สอน Playwright/Postman/CI ให้ดีจึงควรทำให้ผู้เรียนเขียนด้วยมือก่อนและรีวิวผลของ AI เป็นทักษะที่ให้คะแนน. สุดท้าย ความรู้ที่เปิดเผยได้เกี่ยวกับตลาดไทยยังบางกว่าความรู้ระดับโลกมาก ทั้งตัวเลขเงินเดือน สัดส่วนเครื่องมือ และข้อกำหนดกำกับดูแลของ test data ซึ่งเป็นคำถามที่ผู้สอนควรตอบด้วยการสำรวจตลาดและอ่านเอกสาร BOT/PDPA ฉบับจริงเอง ไม่ใช่ด้วยการอ้างตัวเลขที่ยังไม่ยืนยัน.
