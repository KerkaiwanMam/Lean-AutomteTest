## 1. ISTQB CTFL v4.0.1 and CTAL-TAE v2.0: key topics, gTAA, test levels/types, risk-based testing, test techniques

### Takeaway
CTFL v4.0.1 is a 6-chapter, 1,135-minute syllabus (sum of chapter times) in which test design techniques (390 min) and test management (335 min) dominate; it defines 5 test levels, 4 test types, and 4 black-box techniques (EP, BVA, decision table, state transition). CTAL-TAE v2.0 is an 8-chapter, 1,170-minute (sum of chapter times) syllabus that treats test automation as software engineering and defines the gTAA as an abstract interface/capability model (SUT, project mgmt, test mgmt, configuration mgmt interfaces; generation, definition, execution, adaptation capabilities) with a 3-layer TAF (test scripts / business logic / core libraries).

### Cited Findings

**CTFL v4.0.1: structure and meta**
- Version/date: v4.0.1 dated 2024-09-15 is an errata release; v4.0 was the general release on 21.04.2023; v3.1.1 was 01.07.2021 — [CTFL v4.0.1 PDF, p.2-3](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Chapter times: 1 Fundamentals 180 min; 2 Testing throughout the SDLC 130; 3 Static testing 80; 4 Test analysis and design 390; 5 Managing the test activities 335; 6 Test tools 20 (total 1,135 by my addition) — [CTFL v4.0.1 PDF, TOC p.4-7](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Lists 14 Foundation business outcomes, including "Write and communicate clear and understandable defect reports" (FL-BO8), "Work as part of a cross-functional team" (FL-BO10), "Know risks and benefits related to test automation" (FL-BO11), "Identify essential skills required for testing" (FL-BO12) — [CTFL v4.0.1 PDF, section 0.4, p.11](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Seven testing principles: testing shows presence not absence of defects; exhaustive testing impossible; early testing saves time and money; defects cluster together; tests wear out; testing is context dependent; absence-of-defects fallacy — [CTFL v4.0.1 PDF, section 1.3, p.17-18](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Two principal roles: a test management role (planning, monitoring, control, completion) and a testing role (test analysis, design, implementation, execution); one person can hold both, and different people may take them at different times — [CTFL v4.0.1 PDF, section 1.4.5, p.21](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

**CTFL test levels and types (section 2.2, p.28-31)**
- Five test levels: component (unit) testing; component integration testing; system testing; system integration testing; acceptance testing (UAT, operational, contractual, regulatory, alpha, beta). Levels are distinguished by test object, objectives, test basis, defects/failures, approach/responsibilities. Component testing "is normally performed by developers" — [CTFL v4.0.1 PDF](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Four test types: functional, non-functional, black-box, white-box; all four can apply at all levels. Non-functional classification follows ISO/IEC 25010: performance efficiency, compatibility, usability (interaction capability), reliability, security, maintainability, portability (flexibility), safety — [CTFL v4.0.1 PDF](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Confirmation testing confirms a fix; regression testing confirms no adverse side effects, should be preceded by impact analysis, and "is a strong candidate for automation... Test automation should start early" — [CTFL v4.0.1 PDF, 2.2.3, p.30-31](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

**CTFL test techniques (chapter 4, p.39-46)**
- Equivalence partitioning (EP): partitions must be non-overlapping and non-empty; one test per partition is sufficient by theory; coverage = partitions exercised / total partitions (including invalid partitions); for multiple parameters the simplest criterion is "Each Choice" coverage, which ignores combinations — [CTFL v4.0.1 PDF, 4.2.1, p.39-40](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Boundary value analysis (BVA): only for ordered partitions; v4.0 covers 2-value BVA (boundary + closest neighbour in adjacent partition) and 3-value BVA (boundary + both neighbours). Syllabus example: "if (x <= 10)" wrongly coded as "x = 10" is not caught by 2-value data (10, 11) but x=9 from 3-value BVA likely catches it (symbols are garbled in the PDF text extraction; the example is paraphrased) — [CTFL v4.0.1 PDF, 4.2.2, p.40](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Decision table testing: rows = conditions and actions, columns = decision rules; limited-entry (Boolean) vs extended-entry; notation T/F/"-" (irrelevant)/"N/A" (infeasible); coverage items = columns with feasible combinations; rule count grows exponentially, so minimize the table or use a risk-based approach — [CTFL v4.0.1 PDF, 4.2.3, p.41](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- State transition testing: transition labelling "event [guard condition] / action"; state table shows invalid transitions explicitly (empty cells); three coverage criteria: all states, valid transitions (0-switch, "most widely used"), all transitions (valid plus attempted invalid; one invalid transition per test case to avoid defect masking; "minimum requirement for mission and safety-critical software") — [CTFL v4.0.1 PDF, 4.2.4, p.41-42](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- White-box: statement coverage and branch coverage; branch coverage subsumes statement coverage (not vice versa); white-box can miss defects of omission — [CTFL v4.0.1 PDF, 4.3, p.42-43](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Experience-based: error guessing (incl. fault attacks), exploratory testing (simultaneous design/execution/evaluation; session-based with test charter and debrief; useful when specs are poor or time is short; more effective with experienced testers), checklist-based testing — [CTFL v4.0.1 PDF, 4.4, p.43-44](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Collaboration-based: collaborative user story writing, acceptance criteria (scenario-oriented Given/When/Then or rule-oriented), ATDD (specification workshop first; first tests positive, then negative, then non-functional; "acceptance tests then become executable requirements") — [CTFL v4.0.1 PDF, 4.5, p.45-46](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

**CTFL risk-based testing (section 5.2, p.51-53)**
- Risk = potential event with adverse effect; characterized by likelihood and impact (harm) which together give risk level. Project risks (organizational, people, technical, supplier) vs product risks (quality characteristics, e.g., wrong calculations, security vulnerabilities, poor UX) — [CTFL v4.0.1 PDF](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Product risk analysis = risk identification (brainstorming, workshops, interviews, cause-effect diagrams) + risk assessment (categorize, likelihood, impact, level, prioritize); quantitative = likelihood x impact, qualitative = risk matrix. Results drive test scope, levels/types, techniques and coverage, effort estimates, prioritization — [CTFL v4.0.1 PDF, 5.2.3](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Risk control = mitigation + monitoring; responses include mitigation by testing, acceptance, transfer, contingency plan; testing mitigations include choosing testers with right skills, appropriate independence, reviews/static analysis, techniques/coverage level, test types, regression testing — [CTFL v4.0.1 PDF, 5.2.4](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

**CTFL test management, metrics, agile practices**
- Test pyramid: higher layer = lower granularity, lower isolation, higher execution time; bottom layer small/fast/many, top layer few end-to-end tests; original model (Cohn 2009) = unit / service / UI — [CTFL v4.0.1 PDF, 5.1.6, p.50-51](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Testing quadrants (Marick; Crispin 2008): Q1 technology-facing/support team (component + component integration, automated, in CI); Q2 business-facing/support team (functional, examples, story tests, API testing; manual or automated); Q3 business-facing/critique product (exploratory, usability, UAT; often manual); Q4 technology-facing/critique product (smoke and non-functional except usability; often automated) — [CTFL v4.0.1 PDF, 5.1.7, p.51](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Metric families: project progress, test progress, product quality (availability, response time, mean time to failure), defect metrics (found/fixed, defect density, defect detection percentage), risk (residual risk), coverage, cost — [CTFL v4.0.1 PDF, 5.3.1, p.54](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Defect report contents: unique ID, title, date/author, test object and environment, context, reproduction description with logs/screenshots/recordings, expected vs actual, severity, priority, status, references — [CTFL v4.0.1 PDF, 5.5, p.56-57](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Shift left: reviewing specs from a tester's perspective, writing tests before code, CI/CD with automated component tests, static analysis before dynamic testing, non-functional testing from component level; "might result in extra training, effort and/or costs earlier... expected to save efforts and/or costs later" — [CTFL v4.0.1 PDF, 2.1.5, p.27](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- TDD / ATDD / BDD all follow shift left because tests are defined before code; BDD uses Given/When/Then natural language translated into executable tests — [CTFL v4.0.1 PDF, 2.1.3, p.26](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Tester contribution to planning: release planning = write testable user stories and acceptance criteria, participate in risk analysis, estimate test effort, decide approach; iteration planning = detailed risk analysis of stories, testability, break stories into (testing) tasks, estimate. In Agile, exit criteria = Definition of Done, entry criteria for a story = Definition of Ready — [CTFL v4.0.1 PDF, 5.1.2-5.1.3, p.48-49](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Test automation benefits (time saved on repetitive work, consistency, objective coverage measures, faster feedback, more time for deeper tests) and risks (unrealistic expectations, inaccurate estimates, using a tool when manual is more appropriate, over-reliance ignoring critical thinking, vendor/open-source abandonment, incompatibility) — [CTFL v4.0.1 PDF, 6.2, p.59-60](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Syllabus's own career-path text: Foundation holders may go to Core Advanced (Test Analyst, Technical Test Analyst, Test Manager), then Expert (Test Management / Improving the Test Process); also Agile Technical Tester, Agile Test Leadership at Scale; Specialist stream (test automation, AI testing, model-based testing, mobile, performance, security, etc.) — [CTFL v4.0.1 PDF, 0.3, p.10](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

**CTAL-TAE v2.0: structure and meta**

**CTAL-TAE: gTAA and architecture (chapter 3, p.22-28)**
- gTAA = "high-level design concept that provides an abstract view of the communication between test automation and the systems that test automation is connected to": interfaces to the SUT (SUT-to-TAF connection), project management (automation development progress), test management (mapping test case definitions to automated tests), configuration management (CI/CD pipelines, environments, testware) — [CTAL-TAE v2.0 PDF, 3.1.1, p.23](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Four capabilities: test generation (optional, model-based), test definition (separates test definition from SUT/tools), test execution (runner + logging + reporting), test adaptation (adaptors to connect to the SUT via APIs, protocols, services) — [CTAL-TAE v2.0 PDF, 3.1.1, p.23](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- TAA/TAS design must address tool/library selection, plugins, connectivity (firewalls, DB, URLs, mocks/stubs, message queues, protocols), integration with test/defect management, version control — [CTAL-TAE v2.0 PDF, 3.1.2, p.24](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- TAF layering: test scripts layer (test case repository; calls business logic; "no direct calls should be made to the core libraries from test scripts"); business logic layer (SUT-dependent libraries; inherit from or use facades of core libraries); core libraries (SUT-independent, reusable across projects with the same stack). "Keep the number of TAF layers low" — [CTAL-TAE v2.0 PDF, 3.1.3, p.24-25](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Automation approaches with pros/cons: capture/playback (easy start; hard to maintain/scale; no-code vs low-code), linear scripting, structured scripting (reusable test libraries; easy to maintain; needs programming), TDD (red-green-refactor), data-driven testing (same script, different data; needs test data management), keyword-driven testing (keywords from user's perspective; keyword maintenance complex; huge effort for small systems), BDD (Given/When/Then feature files; cons: teams treat it as only a way to write tests, step maintenance is complex, overly complex steps make debugging costly) — [CTAL-TAE v2.0 PDF, 3.1.4, p.25-28](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- "Test automation is a software development activity": OOP principles (encapsulation, abstraction, inheritance, polymorphism), SOLID, and three design patterns named as most important for TAEs: facade, singleton (one driver for the SUT), page object model; flow model = extra facade over page objects (reusable user actions) — [CTAL-TAE v2.0 PDF, 3.1.5, p.28](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)

**CTAL-TAE: other chapters relevant to day-to-day work**
- Advantages/disadvantages and limits: automation checks only what it is programmed to check and only machine-interpretable results with an automated oracle; not all manual tests can be automated; may introduce additional defects — [CTAL-TAE v2.0 PDF, 1.1.1, p.15](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Pilot: evaluate language, tools, levels, cases, approach; try CI/CD integration during the pilot; evaluate team skills/structure/licensing — [CTAL-TAE v2.0 PDF, 4.1.1, p.30](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Maintainability: follow Clean Code principles (common naming, logical project structure, avoid hardcoding, avoid long methods/many parameters, logging, design patterns, testability); use static analyzers and formatters; agreed branching strategy; test fixtures make tests "repeatable and atomic" — [CTAL-TAE v2.0 PDF, 4.2-4.3, p.31-32](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Log levels: Fatal, Error, Warn, Info, Debug, Trace — [CTAL-TAE v2.0 PDF, 4.2.1, p.31](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Pipelines: configuration tests and component tests in the build step as quality gates; component integration tests in CI; system tests can be the last quality gate in continuous deployment; system integration/system/acceptance tests either inside the deployment phase (can fail and roll back, but re-run needs redeploy) or as a separate pipeline triggered after deployment (not a gate); nightly regression and periodic non-functional runs — [CTAL-TAE v2.0 PDF, 5.1.1, p.34-35](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Testware configuration management covers environment config, test data, suites/cases; feature toggles per release/environment, or release testware with the SUT using the same version tags/branches — [CTAL-TAE v2.0 PDF, 5.1.2, p.35](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Contract testing: integration testing that verifies services communicate and data matches agreed rules; "goes beyond schema validation"; consumer-driven vs provider-driven; finds defects earlier — [CTAL-TAE v2.0 PDF, 5.1.3, p.36](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Failure triage procedure (5 steps): check if the failure happened before (known defect in SUT or TAS?); identify the test case; find the failing step; analyze SUT state via screenshots/API/network logs; if SUT state is wrong, log a defect with logs. If actual equals expected, the TAS probably has a defect; if the environment is down, many tests fail at once. Status values: passed, failed, or "TAS failure" (defect not in the SUT). Correlation/trace IDs help — [CTAL-TAE v2.0 PDF, 6.1.1-6.1.2, p.38-41](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Report audiences: management (trends, pass/fail ratio, reliability of TAS and SUT), operational (product use metrics), technical (details); dashboards aggregate pipeline logs, PM tools, repos — [CTAL-TAE v2.0 PDF, 6.1.3, p.41-42](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Unreliable tests: tests with unreliable results (e.g., race conditions) "should be moved from the active automated test suite and analyzed separately"; intermittent failures can be in the test case, SUT, TAF, hardware or network; missing assertions yield inconclusive results — [CTAL-TAE v2.0 PDF, 7.1.2-7.1.3, p.45-46](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Static analysis should also scan test automation code (e.g., plaintext passwords in scripts) — [CTAL-TAE v2.0 PDF, 7.1.4, p.46](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Wait mechanisms ranked: hard-coded waits ("a root cause for many test automation defects") < polling with timeout < subscribing to SUT events (with timeout) — [CTAL-TAE v2.0 PDF, 8.1.2, p.49](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Continuous improvement: "test histogram" to find fragile tests; AI/ML self-healing locators; schema validation for API responses instead of many individual assertions; consolidate overlapping steps into library functions; parallel batch jobs — [CTAL-TAE v2.0 PDF, 8.1.1-8.1.2, p.48-50](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Important absence: v2.0 TAE text contains no defined metric called "flaky rate" or "MTTR" (a text search for flak/intermittent only hits the "intermittent failures" sentence above) — [CTAL-TAE v2.0 PDF](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)

### Inferences
- The 2016-era gTAA is still recognizable in v2.0 (capabilities + interfaces) but v2.0 adds a concrete 3-layer TAF; a Thai course should teach both: gTAA for "what an automation solution must provide" and the 3-layer TAF for "how to structure the repo".
- The TAE syllabus's "test script -> business logic -> core library, no direct core calls from scripts" rule maps directly onto a Playwright/Selenium project: tests -> page/flow objects -> shared fixtures/helpers.
- CTFL techniques (EP/BVA/decision table/state transition) are the vocabulary SDETs use to decide which cases to automate at API level; coverage definitions (e.g., 3-value BVA, all-transitions) are examinable and should be taught with computed examples.
- The CTFL does not define flaky rate, MTTR, defect escape rate; it defines defect detection percentage and defect density. Escape rate is the complement framing of DDP (my inference; formula not in the syllabus).

## 2. Skills matrix and career ladder (manual QA -> automation engineer -> SDET -> QA lead / test architect / QE manager)

### Takeaway
No single authoritative cross-industry ladder exists; public examples differ in names and levels. Verifiable anchors are: ISTQB's own career-path text (Foundation -> Advanced -> Expert; Specialist), the CTAL-TAE statement that a TAE needs software-engineering skill, and a handful of public company frameworks (GitLab SET Associate-to-Principal; Dropbox IC1-IC7 / M3-M7), the latter two confirmed only by search snippets. The per-level competency matrix below is therefore my synthesis, not a quoted source.

### Cited Findings

## 3. Day-to-day work: ceremonies, shift-left, writing/reviewing tests, CI triage, bug reports, exploratory testing, metrics (defect escape rate, flaky rate, MTTR, DORA)

### Takeaway
Daily work spans shift-left collaboration (refinement, three amigos, ATDD/BDD), authoring and reviewing automated tests at the cheapest level possible, triaging CI failures into SUT defect vs test/environment problem, writing reproducible defect reports, and reporting trend metrics to the right audience. Fowler and Google-authored commentary agree: push tests down the pyramid, treat flaky tests as bugs, quarantine them.

### Cited Findings
- Testers in release/iteration planning: write testable stories and acceptance criteria, join risk analysis, break stories into test tasks, estimate — [CTFL v4.0.1 PDF, 5.1.2, p.48-49](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Retrospectives: participants (not only testers) discuss what to keep/improve; recorded in the test completion report — [CTFL v4.0.1 PDF, 2.1.6, p.28](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Whole team approach: any team member with the needed skills can perform any task, everyone is responsible for quality; testers help business reps write acceptance tests and agree test automation approach with developers; may not suit safety-critical contexts needing high independence — [CTFL v4.0.1 PDF, 1.5.2, p.22](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Independence levels: author (none), same-team peer (some), outside team (high), outside organization (very high); drawbacks: isolation, adversarial relations, developers losing sense of responsibility, tester seen as bottleneck — [CTFL v4.0.1 PDF, 1.5.3, p.22-23](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Three Amigos (Cucumber docs): product owner, tester, developer turn user stories into Gherkin scenarios; the tester "generates many scenarios and edge cases, asking how the application might break"; not limited to three people or one session; Example Mapping and Event Storming named as techniques; later Gherkin can be written by a developer/automation specialist plus a tester in pairs, with the PO reviewing — [Cucumber: Who does what](https://cucumber.io/docs/bdd/who-does-what/)
- Practical Test Pyramid (Fowler site): many fast unit tests, fewer integration tests, very few end-to-end tests; avoid the inverted "test ice-cream cone"; end-to-end tests described as notoriously flaky (browser quirks, timing, animations, unexpected popups), slow and costly to maintain; push tests as far down as possible; when a high-level test finds a bug no lower test caught, add a lower-level test; delete high-level tests that add no value; use exploratory testing to find what automation misses and automate the findings; treat test code like production code; consumer-driven contract tests (e.g., Pact) — [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- Non-determinism (Fowler): flaky tests destroy the value of a regression suite because failures get ignored; causes = lack of isolation/shared state, asynchrony (fixed sleeps), remote services, time (wrap the clock), resource leaks; remedy = quarantine immediately, keep quarantine short with a cap on count/age, fix root causes — [Eradicating Non-Determinism in Tests](https://martinfowler.com/articles/nonDeterminism.html)
- Google Testing Blog (2015, Mike Wacker) "Just Say No to More End-to-End Tests": argues unit/integration tests can catch bugs E2E tests are used for, E2E still wanted in small number; critics responded **[UNVERIFIED: post body not fetched; description from search results only]** — [Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)
- Google flakiness data: search summary reported 0.5% of small, 1.6% of medium, 14% of large tests flaky over a week, and Java WebDriver 10.45% vs 1.65% average **[UNVERIFIED: the 2020 post body did not load; numbers from a search-result summary]** — [Google Testing Blog 2020](https://testing.googleblog.com/2020/12/test-flakiness-one-of-main-challenges.html). A comment-thread author reply (Jeff Listfield, 2017 post) says larger tests are more flaky and that when a stable test became flaky due to a code change the cause was a production bug about one-sixth of the time (comment content, not post body) — [Google Testing Blog 2017](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html)
- Google's guiding principle for flaky tests, "When in doubt, doubt the tests first" **[UNVERIFIED: from a search-result summary of the 2016 post]** — [Google Testing Blog 2016](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)
- DORA (page last updated 2026-01-05) lists five software-delivery metrics in two groups: throughput = change lead time, deployment frequency, failed deployment recovery time; instability = change fail rate, deployment rework rate (rework rate is included). The page gives no numeric benchmark thresholds and warns against using the metrics as targets or comparing different applications — [DORA four keys](https://dora.dev/guides/dora-metrics-four-keys/). Older "Four Keys" use "time to restore service" (MTTR) wording per vendor articles; benchmarks like "elite change failure rate 0-15%" came from vendor pages and DORA itself does not give them in the page above — vendor snippets: [Atlassian](https://www.atlassian.com/devops/frameworks/dora-metrics), [Dynatrace](https://www.dynatrace.com/knowledge-base/doras-four-keys/) **[UNVERIFIED: snippets only]**
- Defect metrics defined in ISTQB: defect density, defect detection percentage — [CTFL v4.0.1 PDF, 5.3.1, p.54](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Exploratory testing in practice: session-based, with charter and debrief — [CTFL v4.0.1 PDF, 4.4.2, p.44](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf); Hendrickson's *Explore It!* (Pragmatic Bookshelf, Feb 2013, 186 pp.) describes "small, rapid experiments", charters, and integrating exploration into the development cycle — [Pragmatic Bookshelf](https://pragprog.com/titles/ehxta/explore-it/)

### Inferences
- Metric definitions to teach (my formulations; the first two are not defined in the ISTQB syllabi read): defect escape rate = defects found in production / (defects found pre-release + in production) (complement of DDP); flaky rate = tests with inconsistent outcomes on the same code / total tests (or reruns); MTTR/failed deployment recovery time = time from failed deployment to recovery. Each needs a stated window and data source.
- DORA metrics describe delivery performance, not test quality alone; a tester contributes mainly through change fail rate and recovery time (fast, trustworthy gates; fast diagnosis), and should avoid the Goodhart trap DORA itself warns about.
- Typical week for an SDET (synthesis): refinement/three amigos -> write/review tests with PRs -> keep CI green (triage using the TAE 5-step procedure) -> exploratory session before release -> flaky/quarantine review -> metrics to stakeholders.

### Gaps
- No primary-source data found for a "day in the life" survey (e.g., State of Testing report) because Ministry of Testing pages returned 403.
- Google test-engineer role descriptions (SWE/SET/TE) were not obtained (post body missing); "Software Engineering at Google" ch.14 not read.
- Defect escape rate and flaky rate lack an authoritative standard definition in sources read.

## 4. Mindset and soft skills; common mistakes of junior automation testers

### Takeaway
ISTQB frames the tester's mindset as curiosity, critical thinking and constructive communication (testers are "bearers of bad news"); the TAE syllabus and Fowler/Google sources supply a ready list of automation anti-patterns: UI-heavy suites, fixed sleeps, brittle locators/record-and-playback, hardcoded data, ignoring flaky tests, secrets in scripts.

### Cited Findings
- Soft/hard skills list (testing knowledge; thoroughness, curiosity, attention to detail; communication and active listening; analytical/critical thinking and creativity; technical knowledge; domain knowledge) — [CTFL v4.0.1 PDF, 1.5.1, p.21-22](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- "Testers are often the bearers of bad news... communicating test results may be perceived as criticism of the product and of its author. Confirmation bias can make it difficult to accept information that disagrees with currently held beliefs"; defect information should be communicated in a constructive way — [CTFL v4.0.1 PDF, 1.5.1, p.22](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Testing's psychology: independence helps because the author's and tester's cognitive biases differ — [CTFL v4.0.1 PDF, 1.5.3, p.22](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- Anti-pattern: over-reliance on UI/E2E tests (ice-cream cone; slow, flaky, costly to maintain) — [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- Anti-pattern: capture/playback for anything beyond a small, rarely-changing SUT (hard to maintain, scale, evolve; depends on the SUT version captured) — [CTAL-TAE v2.0 PDF, 3.1.4, p.25-26](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Anti-pattern: locators scattered across tests instead of a page model; page object means one-place update when SUT structure changes — [CTAL-TAE v2.0 PDF, 3.1.5, p.28](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Anti-pattern: hard-coded waits, called a root cause of many automation defects; use polling with timeout or events — [CTAL-TAE v2.0 PDF, 8.1.2, p.49](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf); also [Fowler non-determinism](https://martinfowler.com/articles/nonDeterminism.html)
- Anti-pattern: hardcoded data and no test data management; remedies = data-driven testing, constants, per-environment test data, test data management systems — [CTAL-TAE v2.0 PDF, 4.3.1 p.32, 3.1.4 p.27, 5.1.2 p.35](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Anti-pattern: tests sharing state / no isolation; fixtures should make tests "repeatable and atomic" — [Fowler non-determinism](https://martinfowler.com/articles/nonDeterminism.html); [CTAL-TAE v2.0 PDF, p.31](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Anti-pattern: leaving flaky tests in the main suite (people start ignoring failures) — [Fowler non-determinism](https://martinfowler.com/articles/nonDeterminism.html); [CTAL-TAE v2.0 PDF, 7.1.2, p.45](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Anti-pattern: missing assertions leading to inconclusive tests; plaintext passwords in test code — [CTAL-TAE v2.0 PDF, 7.1.3-7.1.4, p.46](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Anti-pattern: automating without clear objectives or ignoring cost: TAE disadvantages include initial investment, maintenance time, need for clear objectives, rigidity — [CTAL-TAE v2.0 PDF, 1.1.1, p.15](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Anti-pattern: BDD reduced to writing natural-language tests without involving business and developers — [CTAL-TAE v2.0 PDF, 3.1.4, p.28](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTAL-TAE_Syllabus_v2.0.pdf)
- Anti-pattern: treating test code as second-class; Fowler: treat test code with the same care as production code (Arrange-Act-Assert, readable) — [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- Over-reliance on tools "ignoring the need of human critical thinking" is a named risk — [CTFL v4.0.1 PDF, 6.2, p.60](https://www.istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

### Inferences
- "Brittle locators" is not a phrase used in the Fowler article (the fetch summary notes it frames the issue as maintenance cost); the TAE syllabus's framing is locators in one place (page object) plus AI self-healing as an emerging option. Teach: stable test-id attributes and role-based locators as practice, but label it as common industry advice, not an ISTQB statement.
- Whole-team approach implies a junior automation tester should not be a "gatekeeper"; the ISTQB independence drawbacks list (adversarial relationship, bottleneck) is the cited basis.

### Gaps
- No primary study quantifying junior-automation-tester mistakes was found; list is assembled from syllabus and practitioner articles, not survey data.
- "No test data strategy" is supported only indirectly (TAE text on data-driven/test data management).
