## 1. Playwright official best practices (locators, auto-waiting, isolation, fixtures, POM vs fixtures, trace, retries, sharding, parallelism, reporters, CI)

### Takeaway
Playwright's own guidance is: test user-visible behaviour with role/text/test-id locators and web-first assertions, keep every test isolated (own context/storage/data), reuse auth via a setup project + `storageState`, use fixtures for setup/teardown and (optionally) page objects for interaction, record traces `on-first-retry` in CI, shard with `fullyParallel` + blob reports, and use Linux CI with `forbidOnly`, a `globalTimeout` and artifact upload.

### Cited Findings
**Philosophy / locators / assertions (docs: "Best Practices")**
- Test user-visible behaviour, not implementation details (function names, data-structure types, CSS classes) — [Playwright Best Practices](https://playwright.dev/docs/best-practices)
- Keep tests isolated: each test should run independently with its own storage, cookies and data; this aids reproducibility/debugging and prevents cascading failures — [Best Practices](https://playwright.dev/docs/best-practices)
- Share setup with `test.beforeEach` (e.g. sign-in); "a little duplication is acceptable" when it keeps tests clearer; reuse auth via a setup project (log in once) — [Best Practices](https://playwright.dev/docs/best-practices)
- Do not test third-party dependencies; mock external responses with the Network API (`page.route()` + `route.fulfill()`) — [Best Practices](https://playwright.dev/docs/best-practices)
- Control DB data: test against a stable staging environment; keep OS/browser versions consistent for visual regression — [Best Practices](https://playwright.dev/docs/best-practices)
- Locators: prefer user-facing attributes (`page.getByRole('button', { name: 'submit' })`); chain/filter locators (`getByRole('listitem').filter({ hasText: 'Product 2' })`); avoid XPath/CSS tied to DOM structure/classes; `npx playwright codegen <url>` generates role/text/test-id locators — [Best Practices](https://playwright.dev/docs/best-practices)
- Web-first assertions (`await expect(page.getByText('welcome')).toBeVisible()`) wait and retry; do not use manual assertions like `expect(await locator.isVisible()).toBe(true)` which check once without waiting — [Best Practices](https://playwright.dev/docs/best-practices)
- Soft assertions `expect.soft(...)` record failures without stopping the test — [Best Practices](https://playwright.dev/docs/best-practices)
- Lint/type safety: TypeScript + ESLint `@typescript-eslint/no-floating-promises` to catch missing `await`; run `tsc --noEmit` in CI — [Best Practices](https://playwright.dev/docs/best-practices)
- Keep `@playwright/test` up to date so failures are caught before a browser release reaches the public — [Best Practices](https://playwright.dev/docs/best-practices)

**Auto-waiting (docs: "Auto-waiting"/actionability)**
- Before actions Playwright waits for checks: Visible, Stable (same bounding box for 2 consecutive animation frames), Receives Events (not covered by an overlay), Enabled, Editable, Not Inert; which checks apply depends on the action (e.g. click/check/tap = Visible+Stable+Receives Events+Enabled+Not Inert; fill = Visible+Enabled+Editable+Not Inert; focus/press/setInputFiles = none). If checks do not pass within `timeout`, the action fails with `TimeoutError`; `force` skips non-essential checks — [Actionability](https://playwright.dev/docs/actionability)
- Config defaults: per-test `timeout` 30 s; `expect.timeout` 5 s; `globalTimeout` caps the whole run and reporters still produce a report — [Test configuration](https://playwright.dev/docs/test-configuration)

**Fixtures vs Page Object Model**
- POM: a page object represents part of the app; "simplifies authoring" (higher-level API) and "simplifies maintenance" (selectors in one place, reusable code). The official POM page does not mention fixtures — [POM](https://playwright.dev/docs/pom)
- Fixtures encapsulate setup and teardown in one place, are reusable across files, load on demand, can depend on each other; test-scoped fixtures give each test a fresh environment; `{ scope: 'worker' }` fixtures run once per worker; `{ auto: true }` fixtures run for every test (e.g. attach debug logs on failure); `{ option: true }` fixtures expose per-project config. The fixtures page presents POM and fixtures as complementary: the POM class defines how you interact with the page, the fixture creates it, does setup (navigation, seeding), provides it to the test and cleans up — [Fixtures](https://playwright.dev/docs/test-fixtures)

**Setup / auth / data isolation**
- Recommended auth: a setup project logs in once and saves `storageState`; test projects depend on it. Store state in `playwright/.auth` and add to `.gitignore`; the file can contain cookies/headers that allow impersonation, so never commit it; use dedicated test accounts, keep credentials out of source — [Authentication](https://playwright.dev/docs/auth)
- If tests mutate shared server data, use a worker-scoped fixture that logs in once per worker with a unique account (`testInfo.parallelIndex`); API-based login via `APIRequestContext` is faster than UI login; multiple roles = one setup per role + `storageState` per file/group — [Authentication](https://playwright.dev/docs/auth)
- Project dependencies are recommended over `globalSetup`: dependency projects appear in the HTML report, record traces, support fixtures and config options (e.g. `headless`), parallelism and retries; `globalSetup` has none of these. Setup/teardown projects: `teardown: 'cleanup db'` pattern; `--no-deps` skips dependencies — [Global setup and teardown](https://playwright.dev/docs/test-global-setup-teardown)
- Per-worker data isolation example: worker-scoped fixture creates `user-${test.info().workerIndex}` in a test DB and deletes it afterwards; per-test uniqueness via `testInfo.testId` / `testInfo.outputPath()`; named locks `{ lock: 'user-settings' }` serialise tests that share a resource while others stay parallel — [Parallelism](https://playwright.dev/docs/test-parallel)

**Trace viewer**
- Trace Viewer lets you step through each action with before/after DOM snapshots, log, source, network, errors and console; `trace: 'on-first-retry'` is the sample-config default; CI sample uses `retries` 2; `--trace on` forces tracing locally; open via `npx playwright show-report` — [Trace Viewer intro](https://playwright.dev/docs/trace-viewer-intro)
- Best-practices page: on CI use the trace viewer rather than videos/screenshots; record on first retry, not every test, because tracing every test is performance-heavy — [Best Practices](https://playwright.dev/docs/best-practices)

**Retries**
- Retries are off by default; a failed test is re-run (in a fresh worker/browser) until pass or the limit. Result categories: passed (first run), **flaky** (failed first, passed on retry), failed (failed all). Set via config `retries: 3`, CLI `--retries=3`, or `test.describe.configure({ retries: 2 })`; `testInfo.retry` lets code detect a retry (e.g. clear server state). `serial` mode retries the whole group together — [Test retries](https://playwright.dev/docs/test-retries)
- Config page sample: `retries: process.env.CI ? 2 : 0`, `forbidOnly: !!process.env.CI` ("useful on CI"), `workers: process.env.CI ? 1 : undefined`, `reuseExistingServer: !process.env.CI` — [Test configuration](https://playwright.dev/docs/test-configuration)

**Parallelism**
- Test files run in parallel across workers; tests in one file run in order in the same worker; workers are OS processes with their own browser and cannot communicate; after a failure the worker is shut down so the next tests get a clean environment. `fullyParallel: true` parallelises tests within files; `test.describe.configure({ mode: 'parallel' })` per file; `serial` mode is discouraged by the docs ("isolated tests are easier to run independently"). CI workers example: `workers: process.env.CI ? 2 : undefined`; `--workers=1` disables parallelism — [Parallelism](https://playwright.dev/docs/test-parallel)
- Conflict between sample values: CI page says "run one worker on CI to favor stability" (`workers: process.env.CI ? 1 : undefined`) and notes self-hosted machines with more resources can enable parallelism — [CI](https://playwright.dev/docs/ci); parallelism page sample uses 2 — [Parallelism](https://playwright.dev/docs/test-parallel)

**Sharding**
- `--shard=x/y` splits the suite across jobs; by default shards test files, with `fullyParallel: true` it shards at test level (more even; docs recommend for CI); statically skipped tests do not count toward balancing — [Sharding](https://playwright.dev/docs/test-sharding)
- Use the `blob` reporter on CI so shard reports can be merged: `npx playwright merge-reports --reporter html ./all-blob-reports`; GitHub Actions pattern = matrix job (`shardIndex`/`shardTotal`, `fail-fast: false`) uploading `blob-report` artifacts (retention 1 day), then a `merge-reports` job with `if: ${{ !cancelled() }}`, `needs`, `download-artifact` with `merge-multiple` — [Sharding](https://playwright.dev/docs/test-sharding)

**Reporters**
- Built-in: `list` (local default), `line`, `dot` (CI default), `html` (opens on failure by default), `blob`, `json`, `junit`, `github` (failure annotations in Actions). Multiple reporters via array. Docs say avoid the `github` reporter with a matrix strategy because stack traces from each job multiply and clutter the file view — [Reporters](https://playwright.dev/docs/test-reporters)

**CI setup**
- Best practices: run on every commit/PR; use Linux on CI because it is cheaper; install only needed browsers (`npx playwright install chromium --with-deps`); consider sharding — [Best Practices](https://playwright.dev/docs/best-practices)
- CI page: `npm ci` → `npx playwright install --with-deps` → `npx playwright test`; "Always set a global timeout in CI" (example 1 h, keep any job-level timeout higher); official Docker image `mcr.microsoft.com/playwright:v1.64.1-noble`; upload `playwright-report/` (30-day retention) with `if: ${{ !cancelled() }}`; variant using `deployment_status` trigger with `PLAYWRIGHT_TEST_BASE_URL`; fail-fast variant with `--only-changed`; caching browser binaries is discouraged (restore can take as long as download) — [CI](https://playwright.dev/docs/ci)

**Tagging (smoke vs regression)**
- `{ tag: '@smoke' }` or `@token` in title; tags must start with `@`; `--grep` / `--grep-invert`; `grep` also in config/project. The docs do not define smoke/regression suites; running `--grep @smoke` is a usage suggestion built on tag filtering — [Annotations](https://playwright.dev/docs/test-annotations)
- Annotations: `test.skip`, `test.fixme` (not run), `test.fail` (expected to fail; errors if it passes), `test.slow` (triples timeout) — [Annotations](https://playwright.dev/docs/test-annotations)

**Visual comparison**
- `toHaveScreenshot()` snapshots are named per browser/platform; rendering varies with OS, version, hardware, headless mode, so run tests in the same environment where baselines were generated; `threshold` default 0.2, `maxDiffPixels` unset by default; update with `--update-snapshots` — [Visual comparisons](https://playwright.dev/docs/test-snapshots)

### Inferences
- A defensible default `playwright.config.ts` for a course/enterprise repo is: `fullyParallel: true`, `forbidOnly: !!process.env.CI`, `retries: CI ? 2 : 0`, `workers: CI ? 1-2 : undefined` (or shard instead of adding workers), `trace: 'on-first-retry'`, reporter `[['html'], ['junit'], ['github']]` locally/CI single job and `blob` when sharded, `globalTimeout` ≈ 1 h, projects = setup project + browsers (+ tag-filtered projects for smoke).
- Because the official docs treat POM and fixtures as complementary (not competing), the teachable "pro" pattern is: thin page objects (locators + intent-level methods, no assertions of business logic) instantiated by fixtures that also own setup/teardown and data creation.
- The unresolved 1 vs 2 CI workers sample values suggest the number is a tuning choice per runner size, not a rule; sharding is the doc-endorsed scale-out lever.

## 2. Framework architecture: layers, test data management, environments, secrets

### Takeaway
No single official "architecture" standard exists; the practical consensus assembled from Playwright docs, Microsoft's DevOps test guidance, Fowler and Testcontainers is: thin tests on top of page objects / API clients / fixtures, data created per test via API (isolated, unique) rather than shared, disposable real dependencies in containers, and secrets only in the CI secret store (least privilege, OIDC where possible).

### Cited Findings
- Playwright supplies the building blocks of a layered framework: fixtures (setup/teardown/DI), page objects (UI interaction API), `APIRequestContext`/`request` fixture (API client for setup and verification), project dependencies (auth/data setup), config with env-driven values — [Fixtures](https://playwright.dev/docs/test-fixtures); [POM](https://playwright.dev/docs/pom); [API testing](https://playwright.dev/docs/api-testing); [Global setup and teardown](https://playwright.dev/docs/test-global-setup-teardown)
- API layer in Playwright: `baseURL` and `extraHTTPHeaders` (token from `process.env.API_TOKEN`) set once in config; `request` fixture used in tests; create/delete test data via API in `beforeAll`/`afterAll`; pre-conditions created via API then verified in UI; post-conditions verified via API after UI action; `page.request`/`context.request` share cookies with the browser context while `playwright.request.newContext()` is isolated; `context.dispose()` required for standalone contexts — [API testing](https://playwright.dev/docs/api-testing)
- Microsoft test taxonomy: L0/L1 unit tests (no external dependencies), L2 functional tests (assembly + other dependencies such as SQL/file system), L3 functional tests against a testable service deployment (may stub dependencies), L4 integration tests against production; example enforcement: developers run L2 before commit, PR fails if L3 fails, deployment blocked if L4 fails — [Microsoft Learn: Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable) (page `ms.date` 2022-08-18, platform updated 2026-09-04)
- Microsoft principles relevant to framework design: write tests at the lowest possible level; aim for reliability ("Discourage the use of UI tests, because they tend to be unreliable"); functional tests should use only the product's public API; design for testability; treat test code as product code (code review applies); tests live next to product code; code owners are responsible for testing — [Microsoft Learn: Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable)
- Isolation: L2 tests must control their environment and start from known state; leftover data from one test can corrupt another; calling external auth providers for identity is unreliable and violates isolation, so invest in identity support in the test framework — [Microsoft Learn: Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable)
- Fowler (2011): isolation failures come from shared state (database rows, static data, singletons); remedy = rebuild starting state per test or clean up reliably (transaction rollback is one option); replace remote services with test doubles and run contract tests periodically to check the doubles; wrap the clock so time can be frozen — [Fowler, Eradicating Non-Determinism in Tests](https://martinfowler.com/articles/nonDeterminism.html)
- Test code quality (Fowler/Vocke 2018): test one condition per test, favour readability over strict DRY, apply Rule of Three before refactoring; arrange-act-assert / given-when-then — [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- Containers for ephemeral dependencies: Testcontainers runs integration tests against real services in disposable Docker containers instead of mocks/in-memory substitutes; lifecycle is start container in `beforeAll`, run tests, stop in `afterAll`; example: Postgres via `@testcontainers/postgresql`; claim that real DB catches bugs mocks miss (e.g. INT→BIGINT change) — [Testcontainers for Node.js guide](https://testcontainers.com/guides/getting-started-with-testcontainers-for-nodejs/)
- Vocke prefers real local dependencies in integration tests (in-memory H2 DB, WireMock for a third-party API) and says never test against production systems — [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- Ephemeral/preview environments with Playwright: GitHub Actions `deployment_status` trigger with `PLAYWRIGHT_TEST_BASE_URL` set to the deployment URL — [Playwright CI](https://playwright.dev/docs/ci)
- Secrets in GitHub Actions: anyone with write access can read repo secrets so apply least privilege; default `GITHUB_TOKEN` to read-only and raise per job; never store sensitive values as plaintext in workflow files; do not put secrets inside structured JSON/XML/YAML (redaction relies on exact match); register derived values (Base64, JWT) as secrets; if a secret appears in a log delete the log and rotate; environment secrets with required reviewers; remove unused secrets and rotate — [GitHub Docs: Security hardening for GitHub Actions](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)
- Prefer OpenID Connect to authenticate to cloud providers (short-lived scoped tokens instead of long-lived stored credentials); pin third-party actions to full-length commit SHA (tags can be moved); avoid `pull_request_target`, never check out untrusted fork code with it; avoid script injection by passing untrusted expressions via intermediate environment variables — [GitHub Docs: Security hardening](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)
- Playwright credential hygiene: dedicated test accounts, credentials out of source, `storageState` files never committed — [Authentication](https://playwright.dev/docs/auth)

### Inferences
- Suggested layer map for the course repo (synthesis, not a quoted standard): `tests/` (specs, intent only) → `pages/` or `components/` (page objects) → `fixtures/` (compose pages, API clients, data builders, auth) → `api/` (typed clients wrapping `request`) → `data/` (factories/builders producing unique values per test, e.g. suffixing `workerIndex`/`testId`) → `config/` (env-driven `baseURL`, timeouts, projects) → `utils/`. This maps one-to-one to features documented by Playwright (fixtures, POM, `request`, projects, config).
- Data isolation strategy hierarchy implied by the sources: (1) create per-test data via API with unique IDs and clean up; (2) per-worker accounts/data via worker-scoped fixtures; (3) named locks for unavoidable shared resources; (4) serial mode only as last resort (docs discourage it).
- "Seeding" and "ephemeral environments" are supported by the Testcontainers and `deployment_status` evidence, but no source read prescribes a canonical seeding approach.

## 3. Flaky test causes and remedies; quarantine policy; retries vs root cause

### Takeaway
Flakiness is common even at Google (about 1.5% of test runs, almost 16% of tests), is concentrated in larger/UI tests, and the accepted practice is: retry only as a visibility/mitigation device, track and quarantine automatically with an owner and a deadline, and fix root causes (isolation, async waits, time, remote dependencies). Playwright's `flaky` result category and `on-first-retry` trace are designed to support that.

### Cited Findings
- Google (J. Micco, 27 May 2016) says about 1.5% of all test runs report a flaky result; almost 16% of tests have some flakiness; about 84% of observed pass-to-fail transitions in post-submit testing involve a flaky test; an average project with ~1,000 tests at 1.5% would see about 15 failing — [Google Testing Blog (read via mirror, original body did not render)](https://googledirectorynews.blogspot.com/2016/05/flaky-tests-at-google-and-how-we.html); original post: [Flaky Tests at Google and How We Mitigate Them](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)
- Google mitigations: selective rerun of only failed tests, automatic rerun on failure, marking tests flaky so they fail only after 3 consecutive failures (author calls it "hardly a perfect solution": a real break in a 15-minute test could take 45 minutes to surface), an automatic quarantine tool that removes highly flaky tests from the critical path and files a bug (author warns it "could easily mask a real race condition or some other bug"), tooling to detect changes in flakiness and the responsible change, and a dedicated team providing flakiness information — same mirror page above
- Google comment replies (not article body): reruns are used only for tests marked flaky or when users request it; flakiness skews toward UI testing but this is not quantified; Google does not keep an accurate count of times flaky tests mask real bugs — [original post comments](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)
- Google (J. Listfield, 2017) per comments only: larger tests (binary size) were flakier than smaller ones; Android emulator tests stood out; causes cited were absolute timing, relative timing (thread races), random numbers, and timeouts in test/infrastructure code; one team found that when a stable test turned flaky and was traced to a specific change, the cause was a production bug 1/6 of the time — [Where do our flaky tests come from?](https://testing.googleblog.com/2017/04/where-do-our-flaky-tests-come-from.html) (article body did not render; comments only)
- Fowler: non-deterministic tests teach developers to ignore failures and that habit spreads; quarantine flaky tests in a separate suite, do not discard them, limit how many/how long so they get fixed, keep them out of the main deployment pipeline; causes and fixes: lack of isolation (rebuild state/rollback), asynchrony (avoid fixed sleeps, prefer callbacks, else poll with generous timeout), remote services (test doubles + periodic contract tests), time (wrap the clock), resource leaks (small pools expose leaks) — [Eradicating Non-Determinism in Tests](https://martinfowler.com/articles/nonDeterminism.html) (14 Apr 2011)
- Atlassian "Flakinator": flaky tests accounted for up to 21% of master build failures in Jira Frontend (historical) and about 15% of Jira backend failures, wasting over 150,000 developer hours per year on reruns; detection by in-build retry (stops at first flip; 81% detection rate for certain products) plus Bayesian scoring on a moving window producing a 0-1 flakiness score; quarantined tests are isolated from CI but still tracked and still run in branch/scheduled/dedicated quarantine pipelines, released after being healthy for a configured period; owning team identified via code ownership, Jira ticket with deadline, Slack bot; used by 12+ products, recovered 22,000+ builds last quarter, 7,000 unique flaky tests, 350M+ test executions per day — [Atlassian Engineering: Taming test flakiness](https://www.atlassian.com/blog/atlassian-engineering/taming-test-flakiness-how-we-built-a-scalable-tool-to-detect-and-manage-flaky-tests) (post date not shown in fetched text)
- DORA: tests should be reliable (pass = releasable; fail = real defect); "flaky tests should not be tolerated"; a small suite of reliable fast trusted tests beats a large unmaintainable one; prune expensive/unreliable suites; developers should get results in under ten minutes — [DORA: Test automation](https://dora.dev/capabilities/test-automation/) (page last updated 17 July 2025)
- Playwright specifics: a retried test that passes is reported `flaky`; failed workers are replaced; `testInfo.retry` available; traces on first retry; web-first assertions + auto-waiting remove most timing flakiness; avoid fixed sleeps (implied by auto-waiting docs); screenshot baselines are OS/browser dependent so pin environment — [Test retries](https://playwright.dev/docs/test-retries); [Best Practices](https://playwright.dev/docs/best-practices); [Visual comparisons](https://playwright.dev/docs/test-snapshots)
- Microsoft: long-running/unreliable tests breed failure tolerance that "undermines the value of testing"; maintain a high bar for reliability — [Microsoft Learn: Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable)
- Fowler/Vocke: E2E tests are "often flaky, slow, and costly"; keep to a few high-value journeys; push tests down the pyramid — [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)

### Inferences
- Policy template consistent with the sources: (1) CI retries = 1-2 and always report `flaky` as a visible metric (never "green and forget"); (2) flaky test auto-detected (retry-pass) -> ticket with owner and due date -> moved to quarantine suite/tag (e.g. `@quarantine`, excluded via `--grep-invert`) but still run in a scheduled job; (3) exit quarantine after N consecutive green runs; (4) cap quarantine size/age; (5) weekly flaky-rate review (flaky tests / total, mean time to fix).
- Retries trade off: they reduce noise but can hide real races (Google's own warning, 1/6 production-bug finding), so retries are a mitigation, root-cause fixing is the remedy.
- Root-cause taxonomy for teaching: timing/async, shared state/order dependency, test data collisions under parallelism, external dependencies, environment (resources, OS/browser drift for screenshots), time/randomness.

The 2017 findings are from author comments, not the article body.

## 4. CI/CD integration: GitHub Actions pipelines, test selection, quality gates, reporting, artifacts, smoke vs regression, nightly

### Takeaway
Order tests by speed, run fast checks on every PR, gate on explicit signals (exit codes, k6 thresholds, ZAP FAIL rules), upload reports/traces with `if: !cancelled()`, shard and merge blob reports for scale, and use `schedule` (UTC, default branch only) for nightly full regression; limit blast radius with concurrency groups and least-privilege tokens.

### Cited Findings
- Pipelines should order tests by speed and scope for fast feedback; fix lower-level gaps rather than only adding high-level tests — [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- Fast feedback target: results from automated tests in under ten minutes locally and from CI; layered suites (unit, acceptance); continuous curation of suites — [DORA: Test automation](https://dora.dev/capabilities/test-automation/)
- Microsoft example gating: developers run L2 before commit, PR fails on L3 failure, deployment blocked on L4 failure; a Microsoft team reports ~30 minutes from PR to merge including 60,000 unit tests, first CI quality signal about 1 hour, full product tested within about 2 hours of merge — [Microsoft Learn: Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable)
- Playwright GitHub Actions workflow runs on push/PR to main/master, Node LTS, `npm ci`, `npx playwright install --with-deps`, `npx playwright test`, uploads `playwright-report/` for 30 days under `if: ${{ !cancelled() }}`; variants for container image, `deployment_status` trigger, `--only-changed` fail-fast; reporters: HTML default in example; JUnit XML via `['junit', { outputFile: ... }]` (shown for Azure DevOps); Playwright recommends one worker on CI and a global timeout — [Playwright CI](https://playwright.dev/docs/ci)
- Test selection: `--grep`/`--grep-invert` with tags (`@smoke`, `@regression`) in CLI or config projects; `--only-changed` (named in CI page as a fail-fast variant) — [Annotations](https://playwright.dev/docs/test-annotations); [Playwright CI](https://playwright.dev/docs/ci)

- Suggested staged pipeline (synthesis): `lint + tsc + unit` (minutes) -> `API tests (Newman/Postman CLI or Playwright request)` -> `E2E @smoke on PR (single browser)` -> `merge to main: full regression sharded` -> `nightly (cron, UTC offset for Thai time UTC+7): full regression, cross-browser, visual, a11y scan, ZAP baseline, k6 smoke` -> `publish merged HTML report + JUnit`.

## 5. Test pyramid vs trophy vs honeycomb

### Takeaway
All three models answer "where does confidence per cost come from?": Fowler/Vocke keeps many fast unit tests and few E2E; Dodds' trophy emphasises integration tests plus static analysis for UI/JS apps; Spotify's honeycomb emphasises integration tests of a microservice at its edges with few implementation-detail tests and ideally no integrated tests. They are heuristics, not standards.

### Cited Findings
- Practical Test Pyramid (Ham Vocke, published 26 Feb 2018 on martinfowler.com): tests grouped by granularity; two rules of thumb = write tests at different granularities, the higher-level the fewer; Mike Cohn's original layers were unit/service/UI but Vocke calls the names misleading and says teams can use their own names if consistent; warns about the inverted "ice-cream cone"; unit tests are the majority (sociable vs solitary; test through public interface); integration tests check DB/filesystem/other services, usually one at a time; contract tests (consumer-driven, Pact) between services; UI tests don't have to be end-to-end; E2E gives most confidence but often flaky/slow/costly, keep to a few high-value journeys; exploratory testing is manual and bugs found there should become automated tests; avoid duplication and push tests down — [Fowler: The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- Testing Trophy (Kent C. Dodds, published 3 June 2021): four layers End to End, Integration, Unit, Static (2018 tweet: E2E with Cypress, integration/unit with Jest, static with Flow/ESLint); built after his post "Write tests. Not too many. Mostly integration." which responded to a Guillermo Rauch tweet (10 Dec 2016); Static was added because static checking is not a given in JavaScript; principle "the more your tests resemble the way your software is used, the more confidence they can give you"; the article itself does not explicitly describe the section sizes — [Kent C. Dodds: The Testing Trophy and Testing Classifications](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)
- Spotify Testing Honeycomb (A. Schaffer and R. Dybeck, 11 Jan 2018): for microservices most tests are Integration Tests (a service in isolation with realistic inputs/outputs at its interaction points, e.g. spin up DB, start service, query API), a few "Implementation Detail" tests for naturally isolated complex logic, and ideally no "Integrated" tests (those whose pass/fail depends on the correctness of another system; called fragile); rationale: complexity lies in interactions between services and unit tests tie tests to internals; trade-off: tests run in seconds not milliseconds and failures are less precise — [Spotify Engineering: Testing of Microservices](https://engineering.atspotify.com/2018/01/testing-of-microservices/)
- Microsoft: "write tests at the lowest possible level" and discourage UI tests due to unreliability (pyramid-aligned) — [Microsoft Learn: Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable)
- Pact: contract tests avoid reliance on expensive/brittle integration tests; each contract is concrete request/response examples ("contract by example") — [Pact docs](https://docs.pact.io/)

### Inferences
- For a course on Playwright + API + CI, a practical blend: pyramid for logic (unit/API-level), trophy-like emphasis on integration (API/component with real DB via containers) and static analysis (ESLint/tsc), a thin layer of E2E smoke journeys; honeycomb applies when the system under test is a set of microservices (contract tests replace integrated E2E).
- The shapes are about relative proportions; none of the three sources gives numeric ratios (the 70/20/10 ratio is NOT in the sources read).

### Gaps
- UNVERIFIED: Google's 70/20/10 ratio (Google Testing Blog "Just Say No to More End-to-End Tests") — not fetched. Kent Dodds' "Write tests. Not too many. Mostly integration." post and the original Rauch tweet were not fetched directly (only referenced via Dodds' article). Mike Cohn's original pyramid and Fowler's bliki `TestPyramid` not fetched. Dodds' article does not say the Trophy's visual proportions.

## 6. Non-functional automation: performance (k6/JMeter), accessibility (axe + Playwright, WCAG 2.2, % claim), security (ZAP, OWASP Top 10), contract testing (Pact)

### Takeaway
Each non-functional area has an official automation hook that returns pass/fail: k6 thresholds, axe-core via `@axe-core/playwright` with WCAG tags, ZAP baseline exit codes, Pact consumer/provider contracts. For accessibility, automation covers only part of the problem; credible figures differ by method (Deque 57% by issue volume, vendor study; GOV.UK 2017 tool test where 29% of seeded barriers were missed by every tool), and Playwright's docs give no percentage.

### Cited Findings
**Performance (k6)**
- k6 test types: Smoke (minimal load, script sanity), Average-load (5-60 min at typical load), Stress (above average), Soak (average load for hours), Spike (sudden very high load, minutes), Breakpoint (ramp until system breaks); recommends simple patterns (ramp-up, plateau, ramp-down); page does not discuss CI, but says smoke tests fit when system/app code changes — [Grafana k6: Test types](https://grafana.com/docs/k6/latest/testing-guides/test-types/)
- Thresholds encode SLOs as pass/fail (`http_req_failed: ['rate<0.01']`, `http_req_duration: ['p(95)<200']`); failure gives non-zero exit; `abortOnFail` stops early; cloud evaluates thresholds every 60 s — [Grafana k6: Thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/)

**Accessibility**
- WCAG 2.2 is a W3C Recommendation published 12 December 2024; adds 9 success criteria: 2.4.11 Focus Not Obscured (Minimum) AA; 2.4.12 Focus Not Obscured (Enhanced) AAA; 2.4.13 Focus Appearance AAA; 2.5.7 Dragging Movements AA; 2.5.8 Target Size (Minimum) AA; 3.2.6 Consistent Help A; 3.3.7 Redundant Entry A; 3.3.8 Accessible Authentication (Minimum) AA; 3.3.9 Accessible Authentication (Enhanced) AAA; 4.1.1 Parsing is removed (obsolete; authors required to meet 2.0/2.1 may still need to test it); 2.2 content also conforms to 2.0 and 2.1 — [W3C: WCAG 2.2](https://www.w3.org/TR/WCAG22/) (only first ~100k of ~270k characters read, enough for status and "what's new")
- Playwright accessibility docs: automated tests can find e.g. poor colour contrast, unlabelled form controls, duplicate IDs; quote "many accessibility problems can only be discovered through manual testing" and "automated testing cannot detect all types of WCAG violations"; no percentage given; recommends combining with manual assessment (suggests Accessibility Insights for Web). `@axe-core/playwright`: `new AxeBuilder({ page }).analyze()` then assert `violations` is empty; `withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa'])` for A/AA; `include()`, `exclude()` (skips descendants and all rules, use sparingly), `disableRules()`; snapshot a small "fingerprint" (rule ID + targets) of known violations rather than the full array; attach full results with `testInfo.attach()`; a `makeAxeBuilder` fixture centralises config; scan only after the UI reaches the target state — [Playwright: Accessibility testing](https://playwright.dev/docs/accessibility-testing)
- Note the Playwright page's `withTags` example covers WCAG 2.0/2.1 A/AA tags; the fetched summary did not mention 2.2 tags (axe rule tags for 2.2 such as `wcag22aa` were not verified) — [Playwright: Accessibility testing](https://playwright.dev/docs/accessibility-testing)
- Deque study (press release 10 March 2021): on average 57% of accessibility issues were "completely covered" by automated testing with Deque's axe tools; data = anonymised data from 2,000+ audits, 13,000+ pages (first-time assessments), nearly 300,000 issues, HTML only, WCAG 2.0/2.1 A and AA; coverage measured by volume of issues (weighted by severity/impact) rather than by share of WCAG success criteria, which Deque argues understates automation; it challenges the widely cited 20-30% belief; a 2022 Deque report (per a search summary) says 57.38% automated and 80.39% with guided testing (IGT) — [Deque: Automated testing study identifies 57% of digital accessibility issues](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues); 2022 follow-up seen only in search results (UNVERIFIED on the page itself): [Deque coverage report press release](https://www.businesswire.com/news/20220314005559/en/Deque-Stakes-Claim-as-Undisputed-Leader-in-Automated-Accessibility-Testing-Coverage-With-New-Report)
- Caveat on the 57% claim: it is a vendor study run on its own tools and its own audit data; the page gives no independent verification and does not say what the remaining 43% consists of — [Deque blog](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues)
- GOV.UK Digital Service (24 Feb 2017): built a test page ("world's least accessible web page") with 143 accessibility failures in 19 categories and tested 10 free automated tools (count per fetched summary); 42 of 143 barriers (29%) were missed by every tool; tools collectively found 71%; best single tool (Tenon) found 37% counting errors/warnings (Asqatasun 41% when manual-inspection prompts counted), weakest (Google Accessibility Developer Tools) 17%; conclusion: use tools (quick, cheap) but a clean automated result does not mean a page is accessible; combine with manual checks, audit and user testing — [GOV.UK Accessibility blog](https://accessibility.blog.gov.uk/2017/02/24/what-we-found-when-we-tested-tools-on-the-worlds-least-accessible-webpage/)

**Security**
- ZAP Baseline Scan: script in ZAP Docker images; spider runs 1 minute by default, then waits for passive scanning; no active attacks, so docs say it is intended for CI/CD including runs against production sites; all alerts WARN by default; config file (`-c`, generate with `-g`) sets rules to INFO/IGNORE/FAIL; `-r` HTML report (also XML, JSON, Markdown); exit codes 0 success, 1 at least one FAIL, 2 at least one WARN and no FAIL, 3 any other failure; `-I` stops failing on warnings; command `docker run -t ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t https://www.example.com` — [ZAP: Baseline Scan](https://www.zaproxy.org/docs/docker/baseline-scan/)
- OWASP Top 10:2025 categories: A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions; the page gives no exact release date (copyright 2021-2025); owasp.org/Top10 redirects to the 2025 edition — [OWASP Top 10:2025](https://top10.owasp.org/2025)
- Pipeline security hygiene (secrets, SHA pinning, OIDC) — [GitHub Docs: Security hardening](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)

**Contract testing (Pact)**
- Pact is a code-first tool for HTTP and message integrations, "contract by example"; in consumer-driven workflow the contract is generated while running consumer tests, only the parts of the provider actually used are tested so the provider can change unused behaviour; suited to any two communicating services and microservice estates; static schema/OAS files describe all possible states while Pact tests concrete examples; standalone provider testing against an OpenAPI doc does not verify that consumers call the provider correctly — [Pact docs](https://docs.pact.io/)
- Fowler/Vocke: consumers write expectations as tests, publish them, providers run them continuously; the consumer test generates a pact file the provider uses to verify its API — [Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)

### Inferences
- A balanced accessibility message for course text: "Automation is necessary but not sufficient": the 57% (Deque, issue-volume basis) and the GOV.UK 2017 results (29% of seeded barriers undetected by any tool; best tools 37-41%) are not directly comparable (different units: issues in real audits vs seeded failures on a test page), and the older "20-30%" figure is the success-criteria-based estimate Deque disputes. A safe phrasing is "automated tools find a substantial but incomplete share (published estimates range roughly from a third to a bit over half depending on method)", citing both sources.

- ZAP baseline is a safe CI step (passive); active scans/full scans belong in a dedicated pre-prod environment (the baseline page itself does not discuss active scan rules).
- JMeter is not covered by the sources fetched; k6 is the documented option here.

## 8. Shift-left / shift-right, observability-driven testing, testing in production, DORA metrics

### Takeaway
Shift-left moves most testing before merge (fast, reliable, low-level tests); shift-right adds controlled testing and telemetry in production (tiered rollouts, feature flags, fault injection). DORA's five delivery metrics (throughput: lead time, deployment frequency, failed-deployment recovery time; instability: change fail rate, deployment rework rate) are the standard way to measure whether the pipeline helps, and DORA's test-automation capability stresses reliable, fast, developer-owned tests.

### Cited Findings
- Shift-left goal: perform testing earlier so that most testing completes before a change merges to main; long-running last-minute tests build "tolerance for failures"; write more unit tests, run most tests as part of the build; some test classes cannot shift left because they need deployment — [Microsoft Learn: Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable); [Microsoft Learn: Shift right](https://learn.microsoft.com/devops/deliver/shift-right-test-production)
- Shift-right definition: moving some testing later in the DevOps process to test in production using real deployments; benefits: breadth and diversity of the production environment, real customer traffic, evolving demand; especially important for microservices (compatibility across independently deployed versions) and post-deployment quality ("a team is never done with testing in production"); includes monitoring, failover testing and fault injection, tracking failures, exceptions, performance metrics and security events — [Microsoft Learn: Shift right to test in production](https://learn.microsoft.com/devops/deliver/shift-right-test-production) (page `ms.date` 2022-07-21; platform updated 2026-09-04)
- Safe rollout: tier-based deployments and feature flags (example: catch a purchase-blocking bug when under 1% of customers are on the tier); first tier = smallest size needed to run the standard integration suite; subsequent tiers broaden to real users; telemetry stays critical after full rollout — [Microsoft Learn: Shift right](https://learn.microsoft.com/devops/deliver/shift-right-test-production)
- Fault injection / chaos engineering: validates resiliency, containment, incident repair, and trains live-site engineers; automate experiments; limit chaos engineering to canary environments with little or no customer impact; failover testing needs documented plans and regular drills; circuit-breaker example with Redis fallback to SQL — [Microsoft Learn: Shift right](https://learn.microsoft.com/devops/deliver/shift-right-test-production)
- Microsoft scorecard metrics: health/debt (time to detect, time to mitigate, repair items) and velocity; active bugs per developer threshold (more than five bugs per developer triggers prioritising bug fixing before features) — [Microsoft Learn: Shift testing left](https://learn.microsoft.com/en-us/devops/develop/shift-left-make-testing-fast-reliable)
- DORA metrics (page last updated 5 Jan 2026): Throughput = change lead time (version control to production), deployment frequency, failed deployment recovery time; Instability = change fail rate (share of deployments needing immediate fix, e.g. rollback/hotfix), deployment rework rate (share of unplanned deployments triggered by a production incident) — [DORA: Software delivery performance metrics](https://dora.dev/guides/dora-metrics/)
- DORA test automation capability: developers own tests, fast feedback under ten minutes, tests reliable, no tolerance of flaky tests, continuous curation, start small — [DORA: Test automation](https://dora.dev/capabilities/test-automation/) (page last updated 17 July 2025)
- ZAP baseline explicitly designed to be safe against production (passive only) — [ZAP: Baseline Scan](https://www.zaproxy.org/docs/docker/baseline-scan/); Playwright `deployment_status` trigger lets smoke tests run against a deployed URL — [Playwright CI](https://playwright.dev/docs/ci)

### Inferences
- Observability-driven testing, as a teaching framing: after release, treat production telemetry (errors, latency, traces) and synthetic checks (Playwright @smoke against prod-like URL, k6 smoke) as the "tests" for the shift-right phase; tie test-suite health to DORA metrics (e.g. flaky rate affects lead time; escaped defects affect change fail rate). Microsoft's page supports telemetry-as-test-data; no official source read prescribes synthetic monitoring tooling.
- DORA metrics measure delivery performance, not test quality directly; a test-automation program should be reported alongside them (suite duration, flaky rate, escaped defects) but these are not DORA-defined metrics.
- "Testing in production" must be gated by feature flags/tiers/canaries and must avoid destructive tests; read-only smoke and passive scans are safe defaults.
